Задание 15. Система управления доступом API-клиентов (API Client Access Registry)

Программа регистрирует API-клиентов компании и ведёт список разрешённых им сервисов.
Каждый клиент получает идентификатор, название и лимит запросов.
Создайте клиентов, проверьте допустимые изменения их состояния и сформируйте общую сводку.
Диагностические классы показывают доступ к методам из разных пакетов
и порядок выполнения статических и нестатических блоков инициализации.

Задание закрепляет инкапсуляцию, геттеры и сеттеры, модификаторы доступа,
`static`, `final`, статические константы и блоки инициализации.

Используйте Java 17 или Java 21. Сторонние библиотеки не требуются.

## 1. Структура проекта

Создайте пять публичных классов в отдельных Java-файлах.
Четыре класса разместите в пакете `org.study.javarush.java.core.level15.tasks15.g`,
а `ExternalVisibilityDemo` — в пакете `org.study.javarush.java.core.level15.tasks15.g.external`.

Структура относительно каталога `tasks15`:

```text
g/
├── Solution.java
├── ApiClient.java
├── VisibilityProbe.java
├── InitializationProbe.java
└── external/
    └── ExternalVisibilityDemo.java
```

| Класс                    | Назначение                                     |
|--------------------------|------------------------------------------------|
| `Solution`               | Создание клиентов, вызовы методов и отчёт      |
| `ApiClient`              | Инкапсулированное состояние одного API-клиента |
| `VisibilityProbe`        | Проверка четырёх уровней доступа               |
| `InitializationProbe`    | Порядок инициализации класса и объектов        |
| `ExternalVisibilityDemo` | Проверка доступа из другого пакета             |

В `Solution` создайте главный метод программы:

```
public static void main(String[] args)
```

Параметр «аргументы командной строки» (`args`) типа `String[]` здесь не используется.
Данные задаются в коде; ввод через `Scanner` не требуется.
Подключите `java.util.ArrayList` в классах, использующих списки.

`ApiClient` хранит состояние и проверяет операции над ним.
`Solution` использует его публичные методы, формирует отчёт и запускает диагностику.
Два метода статистики `Solution` объявляйте `public static`.
Остальные действия выполняйте в `main`; дополнительные вспомогательные методы не требуются.
Другим классам отдельные методы `main` не нужны.

Постоянный вывод состоит из сообщения статического блока `ApiClient`,
отчёта этапа 22, проверки доступа этапов 24–25 и диагностики этапа 27, в этом порядке.
Контрольные схемы со знаком `→` и промежуточные значения дополнительно печатать не требуется.
Пробелы выравнивания из образцов сохраняйте в строковых литералах.
Квадратные скобки в выводе списков являются частью результата.

## 2. Этап 1. Поля класса `ApiClient`

Объявите шесть приватных полей экземпляра:

| Поле               | Тип                 | Назначение                      |
|--------------------|---------------------|---------------------------------|
| `clientId`         | `String`            | Неизменяемый идентификатор      |
| `displayName`      | `String`            | Отображаемое название           |
| `requestLimit`     | `int`               | Максимум запросов               |
| `usedRequestCount` | `int`               | Количество выполненных запросов |
| `active`           | `boolean`           | Активен ли клиент               |
| `allowedServices`  | `ArrayList<String>` | Список разрешённых сервисов     |

Для `clientId` и `allowedServices` дополнительно укажите `final`.
Поле `allowedServices` инициализируйте новым пустым `ArrayList` при объявлении.
Все поля должны быть `private`; публичные поля для удобства обращения из `Solution` не нужны.

Поля `usedRequestCount` и `active` должны получить стандартные значения Java,
без явного повторного присваивания при создании объекта:

```text
usedRequestCount → 0
active           → false
```

`final` запрещает повторно присвоить идентификатор или заменить ссылку на список.
Содержимое списка при этом может изменяться через методы класса.

## 3. Этап 2. Общие статические поля

Объявите два приватных статических счётчика:

| Поле                    | Тип   | Начальное значение |
|-------------------------|-------|--------------------|
| `nextClientNumber`      | `int` | `1001`             |
| `registeredClientCount` | `int` | `0`                |

* `nextClientNumber`      — следующий номер клиента;
* `registeredClientCount` — количество успешно зарегистрированных клиентов.

Объявите публичную константу максимального лимита:

```
public static final int MAX_REQUEST_LIMIT = 1000;
```

Значение общее для всех API-клиентов; отдельных копий в каждом объекте не требуется.

## 4. Этап 3. Статическая инициализация конфигурации

Объявите публичное статическое поле `DEFAULT_REQUEST_LIMIT` типа `int` с модификатором `final`.
Это лимит запросов по умолчанию. Не задавайте ему значение при объявлении.

Создайте статический блок инициализации.
В нём присвойте `DEFAULT_REQUEST_LIMIT` значение `100`, затем выведите сообщение:

```text
CLIENT CONFIG INITIALIZED
```

Поле получает значение один раз при инициализации класса.
Статический блок не является конструктором и не повторяется при создании каждого клиента.
Вызывать его вручную не нужно.

## 5. Этап 4. Основной конструктор `ApiClient`

Создайте публичный конструктор:

```
public ApiClient(String displayName, int requestLimit)
```

Параметры — название клиента (`displayName`) типа `String`
и лимит запросов (`requestLimit`) типа `int`.

Выполните действия в указанном порядке:

1. Проверьте и сохраните название через `setDisplayName()`.
2. Проверьте и сохраните лимит через `setRequestLimit()`.
3. Присвойте `clientId` строку `"CLIENT-"` с текущим значением `nextClientNumber`.
4. Увеличьте `nextClientNumber`      на единицу.
5. Увеличьте `registeredClientCount` на единицу.

Проверки происходят до назначения идентификатора и увеличения счётчиков.
Если конструктор выбрасывает исключение, регистрация не выполнена:
оба статических счётчика остаются прежними, номер клиента не расходуется.

После первого корректного создания:

```text
clientId              → CLIENT-1001
registeredClientCount → 1
nextClientNumber      → 1002
```

Идентификатор присваивается только при создании объекта.
Публичный метод для его смены не добавляйте.

### Конструктор без параметров

Через `this(...)` задайте название `"Unnamed Client"` и стандартный лимит `100`.
Не дублируйте логику назначения идентификатора и увеличения счётчиков.

## 7. Этап 6. Геттеры для основных данных

Создайте публичные методы экземпляра без параметров:

| Метод                   | Возвращаемый тип |
|-------------------------|------------------|
| `getClientId()`         | `String`         |
| `getDisplayName()`      | `String`         |
| `getRequestLimit()`     | `int`            |
| `getUsedRequestCount()` | `int`            |
| `isActive()`            | `boolean`        |

Каждый метод возвращает соответствующее приватное поле, ничего не меняет и не печатает.
Для логического поля используйте `isActive()`, а не `getActive()`.

Не создавайте `setClientId()` и `setUsedRequestCount()`.
Идентификатор получает значение в конструкторе, а счётчик использованных запросов

## 8. Этап 7. Проверка названия клиента

Создайте публичный сеттер:

```
public void setDisplayName(String displayName)
```

Параметр `displayName` типа `String` — новое название клиента.

1. Сначала проверьте значение на `null`.
2. Затем проверьте пустоту после `trim()` через `isEmpty()`.
3. При некорректном значении выбросьте `IllegalArgumentException`
   с сообщением `"Client name must not be blank."`.
4. При корректном значении сохраните строку после `trim()` в `this.displayName`.

`this.displayName` обозначает поле, а `displayName` — параметр.
Если проверка не пройдена, прежнее название сохраняется.
Сеттер ничего не печатает.

## 9. Этап 8. Проверка лимита запросов

Создайте публичный сеттер:

```
public void setRequestLimit(int requestLimit)
```

Параметр `requestLimit` типа `int` — новый лимит запросов.

Сначала проверьте диапазон от `1` до `MAX_REQUEST_LIMIT` включительно.
При нарушении выбросьте `IllegalArgumentException` с сообщением:

```text
Request limit must be from 1 to 1000.
```

Затем проверьте, что новый лимит не меньше `usedRequestCount`.
Если `requestLimit < usedRequestCount`, выбросьте `IllegalArgumentException` с сообщением:

```text
Request limit below usage.
```

Только после обеих проверок обновите поле текущего объекта.
При ошибке прежний лимит сохраняется. Сеттер ничего не печатает.

## 10. Этап 9. Управление активностью

Создайте публичный сеттер:

```
public void setActive(boolean active)
```

Параметр `active` типа `boolean` — новое состояние активности.
Метод изменяет только `this.active` и ничего не печатает.
Состояние проверяется через `isActive()`; дополнительное публичное поле `isEnabled` не нужно.

При последовательном изменении `false → true → false` название, идентификатор,
лимит и количество использованных запросов не сбрасываются.

## 11. Этап 10. Закрытый метод проверки запроса

Создайте приватный метод экземпляра:

```
private void validateRequestCount(int requestCount)
```

Параметр `requestCount` типа `int` — количество запросов для одной операции.
Значение должно быть строго больше нуля.
Иначе выбросьте `IllegalArgumentException` с сообщением:

```text
Request count must be positive.
```

При корректном значении метод завершается без вывода.
Он не возвращает результат и вызывается только внутри `ApiClient`.
Из `Solution` обращаться к нему напрямую нельзя.

## 12. Этап 11. Выполнение запросов

Создайте публичный метод экземпляра:

```
public boolean tryConsumeRequests(int requestCount)
```

Параметр `requestCount` типа `int` — количество запросов, которое клиент пытается выполнить.

1. Вызовите `validateRequestCount(requestCount)`.
2. Если клиент выключен, верните `false`.
3. Если количество больше доступного остатка, верните `false`.
4. Иначе увеличьте `usedRequestCount` на `requestCount` и верните `true`.

Сравнивайте `requestCount` с разностью `requestLimit - usedRequestCount`.
Не складывайте использованное и запрошенное количество до проверки:
для большого положительного `int` такое сложение может переполниться.

При отказе или исключении счётчик не меняется. Метод сам ничего не печатает.
Даже для выключенного клиента неположительное количество вызывает исключение:
проверка количества выполняется первой.

Это осмысленная операция над объектом, а не произвольное присваивание через сеттер.
Список сервисов в этом задании хранит разрешённые названия,
но `tryConsumeRequests(int)` проверяет только количество и активность.
Проверку доступа к конкретному сервису не добавляйте.

## 13. Этап 12. Вычисляемое свойство

Создайте публичный геттер:

```
public int getAvailableRequests()
```

Он возвращает `requestLimit - usedRequestCount`, ничего не меняет и не печатает.
Отдельное поле `availableRequests` и сеттер для него не нужны:
оставшееся количество вычисляется при каждом обращении,
а не хранится как ещё одно поле.

## 14. Этап 13. Список разрешённых сервисов

Названия разрешённых внутренних сервисов храните в `allowedServices`.
Создайте публичный метод экземпляра:

```
public void addAllowedService(String serviceName)
```

Параметр `serviceName` типа `String` — добавляемое название сервиса.

1. Сначала проверьте значение на `null`.
2. Затем проверьте пустоту после `trim()` через `isEmpty()`.
3. При некорректном значении выбросьте `IllegalArgumentException`
   с сообщением `"Service name must not be blank."`.
4. Удалите пробелы по краям через `trim()`.
5. Проверьте очищенное название через `contains()`.
6. Если оно уже присутствует, завершите метод без добавления дубликата.
7. Иначе добавьте название через `add()`.

Сравнение регистрозависимое: `"billing"` и `"Billing"` — разные названия.
Метод ничего не печатает; при ошибке список сохраняет прежнее содержимое.

## 15. Этап 14. Защищённый геттер списка

Создайте публичный метод экземпляра:

```
public ArrayList<String> getAllowedServices()
```

Метод без параметров возвращает новый список с элементами внутреннего `allowedServices`.
Можно использовать конструктор `ArrayList`, принимающий другую коллекцию.
Каждый вызов должен предоставлять отдельную копию, а не внутреннее поле.

Внешний код может просматривать и изменять полученный список.
Это не должно менять внутренний список клиента.
Метод ничего не печатает и не изменяет состояние клиента.

`private` у поля недостаточно, если публичный метод возвращает наружу
ссылку на изменяемый внутренний объект.

## 20. Этап 19. Проверка защитных сеттеров

Объявите три переменные типа `String` с начальным значением `""`:

Пробелы после подписи должны соответствовать отчёту этапа 22.
Не печатайте сообщения из `catch`: все три строки выводятся позже, в составе отчёта.

## 21. Этап 20. Проверка защитной копии

Получите `paymentClient.getAllowedServices()` и сохраните результат в

Название второго остаётся `"Test Client"`, лимиты сохраняют значения `100` и `200`.
Идентификаторы различаются: `CLIENT-1001` и `CLIENT-1002`; общий счётчик равен `2`.

### Дополнительный тест 8. Статическая инициализация при повторном запуске

Восстановите основной сценарий и запустите `Solution` дважды как два отдельных процесса Java.
В каждом запуске счётчики начинают с начальных значений,
первый клиент получает `CLIENT-1001`, статические блоки выполняются по одному разу.
Вывод должен соответствовать основному тесту.
Счётчики не сохраняются между независимыми запусками приложения.

## 32. Критерии выполнения

Задание завершено, если:

1. Пять публичных классов находятся в указанных двух пакетах и компилируются на Java 17 или Java 21.
2. `ApiClient` защищает поля, присваивает идентификатор только при создании объекта,
   проверяет изменения через сеттеры и контролирует выполнение запросов по этапам 1–15.
3. Геттеры возвращают текущие значения; копия списка не позволяет менять внутреннюю коллекцию.
   Общие счётчики учитывают только успешное создание клиентов.
4. Основной отчёт и все восемь дополнительных тестов дают описанные результаты.
5. Проверки доступа и порядка инициализации соответствуют этапам 23–27.
   Все десять экспериментов выполнены отдельно, временные изменения убраны.
6. Вы можете объяснить различия между `public`, `protected`, package-private и `private`,
   между `static`, `final` и `static final`, а также роль геттеров, сеттеров и защитных копий.
7. Вы можете объяснить, почему не каждому полю нужен публичный сеттер
   и почему возврат внутренней изменяемой коллекции нарушает инкапсуляцию.

Наследование, интерфейсы, полиморфизм, база данных, HTTP-запросы
и сторонние библиотеки для задания не требуются.
