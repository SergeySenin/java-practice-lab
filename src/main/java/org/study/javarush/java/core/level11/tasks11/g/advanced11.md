Задание 11. Система проверки пакетных выплат (Payout Batch Validator)

Программа обрабатывает файл с заявками на выплаты партнёрам маркетплейса: проверяет структуру
и числовые данные каждой записи, рассчитывает выплату, отклоняет некорректные записи
и продолжает обработку остальных. Ошибки работы с самим файлом обрабатываются отдельно.
Отдельная диагностическая программа показывает
необработанные исключения и стек вызовов (Stack Trace).

Задание закрепляет обработку исключений (`catch`),
самостоятельную генерацию исключений (`throw`),
передачу ответственности вызывающему методу (`throws`) и управление файловыми ресурсами.

Используйте Java 17 или Java 21. Сторонние библиотеки не требуются.

## 1. Структура проекта

Создайте два файла в одном пакете задания:

* `Solution.java`           — публичный класс «решение» (`Solution`);
* `ExceptionTraceDemo.java` — публичный класс
  «демонстрация стека исключений» (`ExceptionTraceDemo`).

В обоих классах создайте главный метод программы (`main`):

```
public static void main(String[] args)
```

Параметр «аргументы командной строки» (`args`) типа `String[]` здесь не используется.
Классы запускайте отдельно: `Solution` выполняет импорт выплат и обрабатывает ожидаемые ошибки,
а `ExceptionTraceDemo` намеренно завершается с необработанным исключением.

В `Solution` подключите `java.io.BufferedReader`, `java.io.FileReader`, `java.io.IOException`
и `java.util.Scanner`. Все вспомогательные методы обоих классов объявляйте `public static`.
Имена, типы и порядок параметров сохраняйте по соответствующим этапам.

Для сообщений используйте `System.out.println()`, подставляя значения конкатенацией (`+`).
Пробелы выравнивания из образцов записывайте внутри строковых литералов.
Обозначения в квадратных скобках заменяйте соответствующими значениями;
сами скобки и поясняющий текст внутри них не печатайте.

Считайте, что количество физических строк, оба счётчика и общая сумма принятых выплат
помещаются в `int`. Отдельную проверку переполнения не добавляйте.
Не требуется создавать собственные классы исключений, использовать многопоточность,
базу данных, внешние библиотеки или действительно переводить денежные средства.

## 2. Этап 1. Индексы статистики

За пределами методов `Solution` объявите три константы
с модификаторами `private static final` и типом `int`:

| Константа              | Значение | Назначение                    |
|------------------------|---------:|-------------------------------|
| `ACCEPTED_COUNT_INDEX` |      `0` | Количество принятых заявок    |

## 3. Этап 2. Подготовка файла с заявками

Используйте текстовый файл `src/main/resources/payouts.txt`. Если файла ещё нет, создайте его.
Для основного теста он должен содержать ровно семь строк:

```text
PAY-101;1200;100
PAY-102;bad;50
PAY-103;700;900
PAY-104;500;0
ORD-105;1000;100
PAY-106;400
PAY-107;200;20
```

Формат записи — три поля, разделённые точкой с запятой:

```text
идентификатор;начисленная_сумма;комиссия
```

Строка `PAY-101;1200;100` означает: начислено `1200`, комиссия `100`, к выплате `1100`.
В исходных данных намеренно присутствуют разные ошибки. Исправлять эти строки не нужно.

Рабочий каталог запуска — корень проекта. В IntelliJ IDEA прожмите
**Run Configuration → Working directory** значение `$PROJECT_DIR$`.
Путь `src/main/resources/payouts.txt` отсчитывается от этого каталога.
Программа читает оригинал файла напрямую; в тестах редактируйте этот же файл.
Исходные данные хранятся в Git, где можно просмотреть изменения и восстановить содержимое.

## 4. Этап 3. Получение пути к файлу

В `Solution.main` создайте «консоль» (`console`) типа `Scanner`, связанную с `System.in`.
Через `nextLine()` считайте «исходный путь к файлу» (`filePathInput`) типа `String`.
Создайте «путь к файлу» (`filePath`) типа `String`: результат `trim()` для `filePathInput`.

Основной ввод:

```text
src/main/resources/payouts.txt
```

За один запуск считывайте только одну строку пути.
Сами заявки программа получает из файла, а не из `Scanner`.

## 5. Этап 4. Метод проверки и расчёта выплаты

В `Solution` создайте метод «проверить и рассчитать выплату» (`validateAndCalculatePayout`):

```
public static int validateAndCalculatePayout(String payoutRecord)
```

Параметр «запись выплаты» (`payoutRecord`) — одна непустая строка из файла.
Метод возвращает сумму выплаты для корректной записи и сам ничего не печатает.

Выполняйте проверки в порядке подразделов ниже. При первой ошибке исключение завершает метод:
остальные проверки этой записи и расчёт выплаты не выполняются.

### Разделение записи

Через `payoutRecord.split(";", -1)` создайте массив «поля выплаты» (`payoutFields`)
типа `String[]`. Второй аргумент `-1` сохраняет пустые поля, включая последнее.

До обращения по индексам проверьте количество полей. Если оно не равно `3`,
самостоятельно выбросьте `IllegalArgumentException` с сообщением:

```text
Invalid payout record structure: [исходная строка]
```

Подставьте исходный `payoutRecord` без удаления пробелов.
Используйте `throw new IllegalArgumentException(...)`.

### Идентификатор выплаты

Из первого поля получите «идентификатор выплаты» (`payoutId`) типа `String`,
удалив пробелы по краям через `trim()`.

Допустимый идентификатор одновременно:

* начинается с `"PAY-"` с учётом регистра;
* содержит хотя бы один символ после префикса.

Требовать только цифры в суффиксе или проверять уникальность идентификатора не нужно.
При нарушении правила выбросьте `IllegalArgumentException` через `throw new` с сообщением:

```text
Invalid payout identifier: [payoutId]
```

### Преобразование числовых полей

Последовательно получите две переменные типа `int`:

* «начисленная сумма»  (`grossAmount`) — второе поле;
* «комиссия платформы» (`platformFee`) — третье поле.

Для каждого поля примените `trim()`, затем `Integer.parseInt()`.
Не перехватывайте `NumberFormatException` внутри `validateAndCalculatePayout`:
если преобразование невозможно, исключение передаётся вызывающему коду.

### Бизнес-проверка

После преобразования обоих чисел проверьте:

* `grossAmount` строго больше `0`;
* `platformFee` не меньше `0` и строго меньше `grossAmount`.

Если хотя бы одно условие нарушено, выбросьте `IllegalArgumentException` через `throw new`:

```text
Invalid payout values: [payoutId]
```

### Расчёт результата

Создайте «сумму к выплате» (`payableAmount`) типа `int`:
разность `grossAmount` и `platformFee`. Верните её через `return`.

Примеры:

```text
PAY-101;1200;100 → 1100
PAY-104;500;0    → 500
PAY-107;200;20   → 180
```

При недопустимых данных исключение создаёт ваша программа через `throw`.
При ошибке `Integer.parseInt()` его создаёт библиотека Java.

## 6. Этап 5. Метод чтения файла

В `Solution` создайте метод «прочитать файл выплат» (`readPayoutFile`):

```
public static int[] readPayoutFile(String filePath) throws IOException
```

Параметр `filePath` — путь к файлу.
Через `new` создайте массив «статистика выплат» (`payoutStatistics`) типа `int[]` длиной `3`.
Все элементы сначала равны `0`; их назначение определяют константы этапа 1.

### Открытие файла

Создайте `FileReader` для `filePath` и оберните его в `BufferedReader`.
Ресурс «читатель файла выплат» (`payoutReader`) типа `BufferedReader`
объявите в конструкции `try-with-resources`.

При выходе из блока ресурс закрывается автоматически, в том числе при исключении.
Не вызывайте `close()` вручную в `finally`.

### Чтение строк

Создайте:

* «текущая запись выплаты» (`payoutRecord`)   типа `String`;
* «номер строки файла»     (`fileLineNumber`) типа `int` с начальным значением `0`.

Циклом `while` считывайте строки через `payoutReader.readLine()`, пока результат не равен `null`.
Для каждой прочитанной физической строки увеличивайте `fileLineNumber` на единицу.

Если `payoutRecord.trim().isEmpty()` возвращает `true`, пропустите строку через `continue`.
Такие строки не считаются принятыми или отклонёнными, но учитываются в нумерации.
Результат `trim()` не присваивайте обратно: исходная запись нужна для сообщения об ошибке структуры.

### Обработка записи

Для каждой непустой строки создайте внутренний блок `try` с двумя обработчиками `catch`.
Внутри `try` передайте `payoutRecord` в `validateAndCalculatePayout`.
Результат сохраните в «рассчитанную выплату» (`calculatedPayout`) типа `int`.

Только после успешного возврата:

1. увеличьте на единицу элемент `payoutStatistics` с индексом `ACCEPTED_COUNT_INDEX`;
2. прибавьте `calculatedPayout` к элементу с индексом `TOTAL_PAYOUT_INDEX`;
3. выведите сообщение по шаблону ниже.

```text
Line [номер]: ACCEPTED, amount: [сумма]
```

Вместо номера подставьте `fileLineNumber`, вместо суммы — `calculatedPayout`.
Каждую непустую запись учитывайте ровно один раз: как принятую или как отклонённую.

### Первый `catch`: некорректное число

Первый обработчик — `catch (NumberFormatException exception)`.
Параметр «перехваченное исключение» (`exception`) доступен внутри этого обработчика.

Увеличьте на единицу элемент `payoutStatistics` с индексом `REJECTED_COUNT_INDEX`.
Выведите сообщение с `fileLineNumber`:

```text
Line [номер]: REJECTED - NUMBER_FORMAT
```

Следующей строкой выведите префикс `"Reason: "` и результат `exception.getMessage()`.
Текст сообщения `NumberFormatException` может зависеть от реализации и версии Java:
проверяйте тип исключения и смысл сообщения, а не посимвольное совпадение его текста.

### Второй `catch`: нарушение правил

Следующий обработчик — `catch (IllegalArgumentException exception)`.
Имя `exception` здесь относится к параметру этого отдельного обработчика.

Увеличьте на единицу элемент `payoutStatistics` с индексом `REJECTED_COUNT_INDEX`.
Выведите сообщение с `fileLineNumber`:

```text
Line [номер]: REJECTED - VALIDATION
```

Следующей строкой выведите `"Reason: "` и `exception.getMessage()`.
Это сообщение, заданное при создании исключения на этапе 4.

`NumberFormatException` должен идти раньше `IllegalArgumentException`,
поскольку является его подклассом. Не добавляйте здесь `catch (Exception exception)`.
После любого из двух обработчиков продолжайте цикл со следующей строкой.

### Возврат статистики

После завершения `try-with-resources` верните `payoutStatistics`.
Ошибки открытия, чтения и закрытия файла (`IOException`) внутри метода не перехватывайте:
в сигнатуре для них указан `throws IOException`.

## 7. Этап 6. Метод запуска импорта

В `Solution` создайте метод «запустить импорт выплат» (`runPayoutImport`):

```
public static int[] runPayoutImport(String filePath) throws IOException
```

Параметр `filePath` — путь к файлу. Сначала выведите:

```text
IMPORT STARTED: [filePath]
```

Затем вызовите `readPayoutFile(filePath)` и верните полученный массив статистики.
Не размещайте внутри `runPayoutImport` обработчик `IOException`.

Порядок вызовов:

```text
main
  ↓
runPayoutImport
  ↓
readPayoutFile
  ↓
FileReader / BufferedReader
```

При ошибке работы с файлом исключение передаётся в обратном направлении:
через `readPayoutFile` и `runPayoutImport` к обработчику в `main`.
`throws IOException` сообщает вызывающему коду о возможной передаче проверяемого исключения
(checked exception); само объявление `throws` не создаёт и не обрабатывает исключение.

## 8. Этап 7. Обработка `IOException` в `main`

В `Solution.main` после получения `filePath` создайте конструкцию `try-catch-finally`.

В блоке `try`:

* вызовите `runPayoutImport(filePath)`;
* сохраните возвращённый массив в «результат импорта» (`importStatistics`) типа `int[]`;
* выведите итоговую сводку по этапу 8.

В обработчике `catch (IOException exception)` выведите:

```text
IMPORT FAILED: unable to read [filePath]
```

Не заменяйте его на общий `catch (Exception exception)`.
В блоке `finally` выведите:

```text
IMPORT ATTEMPT FINISHED
```

Эта строка появляется и после успешного импорта, и после ошибки работы с файлом.
Не используйте `return` внутри `finally`.

## 9. Этап 8. Итоговая сводка

В успешной ветке `try` из этапа 7 выведите значения `importStatistics`
через константы индексов этапа 1. Формат:

```text
Accepted:      [количество]
Rejected:      [количество]
Payable total: [сумма]
```

Сводка появляется только после успешного возврата `runPayoutImport`:
файл прочитан до конца и ресурс закрыт без ошибки.

Если открытие, чтение или закрытие завершилось с `IOException`, обработчик в `main`
выводит сообщение об ошибке, а сводка не печатается.
Сообщения отдельных записей, выведенные до ошибки, остаются в консоли.

## 10. Основной тест

Запустите `Solution`. В файле должны быть семь строк этапа 2.
Ввод в консоль:

```text
src/main/resources/payouts.txt
```

Ожидаемый вывод; переменная часть сообщения исключения обозначена в квадратных скобках:

```text
IMPORT STARTED: src/main/resources/payouts.txt
Line 1: ACCEPTED, amount: 1100
Line 2: REJECTED - NUMBER_FORMAT
Reason: [сообщение NumberFormatException]
Line 3: REJECTED - VALIDATION
Reason: Invalid payout values: PAY-103
Line 4: ACCEPTED, amount: 500
Line 5: REJECTED - VALIDATION
Reason: Invalid payout identifier: ORD-105
Line 6: REJECTED - VALIDATION
Reason: Invalid payout record structure: PAY-106;400
Line 7: ACCEPTED, amount: 180
Accepted:      3
Rejected:      4
Payable total: 1780
IMPORT ATTEMPT FINISHED
```

В строке сразу после `Line 2: REJECTED - NUMBER_FORMAT` выведите `"Reason: "`
и фактический результат `exception.getMessage()`:
он объясняет невозможность преобразования `"bad"` в `int`.
Текст `[сообщение NumberFormatException]` буквально не печатайте.
Остальные строки должны совпасть с образцом, включая пробелы выравнивания.

Проверочные значения:

| Показатель               | Результат |
|--------------------------|----------:|
| Прочитано непустых строк |         7 |
| Принято выплат           |         3 |
| Отклонено выплат         |         4 |
| Общая сумма выплат       |      1780 |

Ошибка одной заявки не должна прекращать обработку следующих.

## 12. Этап 10. Отдельная демонстрация исключений

Работайте в `ExceptionTraceDemo.java`. Этот класс не участвует в импорте выплат
и запускается отдельно для изучения поведения Java.

### Метод с обработкой исключения

Создайте метод «показать обработанное арифметическое исключение»
(`demonstrateHandledArithmeticException`) с модификаторами `public static`.
Возвращаемый тип — `void`, параметров нет.

Объявите две локальные переменные типа `int`:

* «числитель» (`numerator`)   — `100`;
* «делитель»  (`denominator`) — `0`.

В блоке `try` попытайтесь создать «результат деления» (`divisionResult`) типа `int`,
присвоив ему результат целочисленного деления `numerator` на `denominator`.
В `catch (ArithmeticException exception)` выведите префикс `"HANDLED ARITHMETIC ERROR: "`
и сообщение `exception.getMessage()`.

После `try-catch` выведите `"EXECUTION CONTINUED"`.
Результат:

```text
HANDLED ARITHMETIC ERROR: / by zero
EXECUTION CONTINUED
```

После обработки исключения выполнение продолжается.
Операция деления не завершилась, поэтому значение `divisionResult` не было получено.

### Цепочка вызовов для Stack Trace

Создайте два метода с модификаторами `public static`, возвращаемым типом `void`
и без параметров:

* «запустить диагностическую цепочку» (`runDiagnosticChain`);
* «вызвать диагностическую ошибку»    (`triggerDiagnosticFailure`).

В `runDiagnosticChain` вызовите `triggerDiagnosticFailure()`.
В `triggerDiagnosticFailure` объявите собственные локальные `numerator` и `denominator`
типа `int` со значениями `100` и `0`.
Попытайтесь присвоить результат их целочисленного деления локальной `divisionResult` типа `int`.

Имена повторяются в разных методах и относятся к разным локальным переменным.
Не перехватывайте исключение в этих двух методах.

### Главный метод диагностического класса

В `ExceptionTraceDemo.main` сначала вызовите `demonstrateHandledArithmeticException()`.
Затем создайте `try-finally` без `catch`:
в `try` вызовите `runDiagnosticChain()`, а в `finally` выведите:

```text
DIAGNOSTIC FINISHED
```

При запуске возникнет необработанное `ArithmeticException`.
Программа завершится с ошибкой, а JVM выведет настоящую трассировку.
В ней должна быть видна цепочка:

```text
ExceptionTraceDemo.triggerDiagnosticFailure(...)
ExceptionTraceDemo.runDiagnosticChain(...)
ExceptionTraceDemo.main(...)
```

Номера строк зависят от расположения кода. Полное имя класса также включает пакет задания.
`finally` выполняется и выводит своё сообщение даже при этом необработанном исключении.
В некоторых консолях строки `System.out` и трассировка из потока ошибок могут
отображаться вперемешку; их визуальное расположение не меняет порядок выполнения команд.

## 13. Этап 11. Анализ Stack Trace

После запуска `ExceptionTraceDemo` определите:

1. Тип исключения и его сообщение.
2. Метод и строку исходного кода, где произошло деление на ноль.
3. Метод, вызвавший ошибочный метод, и всю цепочку до `main`.

## 14. Диагностические эксперименты

Выполняйте опыты по одному после успешного основного теста.
После каждого удаляйте временные объявления и вывод, восстанавливайте рабочие обработчики
и сигнатуры; ошибочные строки удаляйте или комментируйте.
Затем повторяйте основной тест `Solution` с исходными семью строками файла.

Изменения разных опытов не объединяйте. В итоговом диагностическом классе
должны остаться обработанное и необработанное деление на ноль из этапа 10.

### Диагностический эксперимент 1. Исключение прерывает `try`

В `demonstrateHandledArithmeticException` внутри `try`, сразу после попытки деления,
временно добавьте вывод:

```text
AFTER DIVISION
```

Эта команда не должна выполниться.
Объясните, почему управление сразу переходит в соответствующий `catch`.

### Диагностический эксперимент 2. `getMessage()`

В обработчике `ArithmeticException` временно замените сообщение с префиксом
на вывод только `exception.getMessage()`. Запустите `ExceptionTraceDemo`.
При отдельном запуске замените этот вывод вызовом `exception.printStackTrace()`.

Сравните сообщение исключения и подробную трассировку.
Не путайте эту трассировку обработанного исключения с последующей трассировкой
необработанной ошибки из `triggerDiagnosticFailure`.
После опыта верните исходный вывод обработчика.

### Диагностический эксперимент 3. Неверный порядок `catch`

В `readPayoutFile` временно поменяйте местами обработчики:
сначала `IllegalArgumentException`, затем `NumberFormatException`.

Ожидается ошибка компиляции: более узкий обработчик недостижим,
поскольку `NumberFormatException` уже перехватывается как подкласс `IllegalArgumentException`.
Восстановите исходный порядок.

Объясните, почему слишком общий `catch` мешает различать причины ошибок
и почему в рабочей версии не используется `catch (Exception exception)`.

### Диагностический эксперимент 4. Пустой `catch`

Временно уберите все действия из `catch (NumberFormatException exception)`
в `readPayoutFile`. Запустите основной тест.

Сравните статистику и сообщения с исходным образцом.
Объясните, почему пропали сведения об отклонённой записи и причина ошибки.
После опыта восстановите обработчик: пустой `catch` в итоговой программе не оставляйте.

### Диагностический эксперимент 5. `NullPointerException`

В `triggerDiagnosticFailure` временно замените все действия с делением:

* создайте «диагностический текст» (`diagnosticText`) типа `String` со значением `null`;
* вызовите у него `length()`.

Не перехватывайте исключение. Запустите `ExceptionTraceDemo`
и изучите `NullPointerException` в трассировке диагностической цепочки.
После опыта восстановите деление на ноль.

### Диагностический эксперимент 6. `ArrayIndexOutOfBoundsException`

В `triggerDiagnosticFailure` временно замените все действия с делением:

* через `new` создайте массив «диагностические значения» (`diagnosticValues`)
  типа `int[]` длиной `3`;
* попытайтесь вывести элемент `diagnosticValues[10]` через `System.out.println()`.

Запустите `ExceptionTraceDemo`. Ожидается `ArrayIndexOutOfBoundsException`
с трассировкой через те же вызывающие методы. Исключение не перехватывайте.
После опыта восстановите исходный код метода.

### Диагностический эксперимент 7. Проверяемое исключение

Временно удалите `throws IOException` из сигнатуры `readPayoutFile`,
не добавляя обработчик `IOException` внутри метода.
Получите ошибку компиляции и восстановите объявление.

Затем отдельно повторите опыт с `runPayoutImport`, сохраняя рабочую сигнатуру `readPayoutFile`.
Верните `throws IOException` в `runPayoutImport`.

Объясните отличие проверяемых (checked) исключений от непроверяемых (unchecked).
Для `IOException` компилятор требует обработку или объявление передачи;
непроверяемые исключения в диагностических методах можно не указывать в `throws`.
