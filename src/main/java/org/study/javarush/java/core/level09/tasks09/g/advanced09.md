Задание 09. Анализатор журналов инцидентов (Incident Log Analyzer)

Вы разрабатываете консольную программу для анализа одной записи системного журнала (`log`).

Программа получает необработанную строку, содержащую сведения об инциденте, разделяет её на
отдельные поля, очищает и проверяет данные, извлекает полезные части строк, формирует
диагностическую статистику и собирает итоговый отчёт.

Основная цель задания — закрепить полноценную работу со строками (`String`) и построителем строк
(`StringBuilder`).

## 1. Структура программы

Создайте класс «решение» (`Solution`).

Создайте главный метод программы (`main`).

Подключите:

```
java.util.Locale
java.util.Scanner
```

Для чтения данных создайте объект «консоль» (`console`) типа `Scanner`.

Для задания используйте Java 17 или Java 21.

## 2. Этап 1. Формат входной строки

Программа должна получить через `nextLine()` одну строку следующего формата:

```text
код | уровень | сервис | email | путь к журналу | сообщение
```

Для основного теста введите:

```text
   INC-5042   |   error   |   auth-service   |   User@Example.com   |   C:\Logs\auth.log   |   Invalid password for "admin"
```

В одной строке содержится шесть полей.

Между значениями и символами `|` специально находятся лишние пробелы.

## 3. Этап 2. Разделение строки

Создайте переменную:

«части записи журнала» (`logParts`) типа:

```
String[]
```

Разделите исходную строку методом:

```
split()
```

Разделителем является символ:

```text
|
```

Помните, что параметр `split()` является регулярным выражением (`regex`), а символ `|` имеет
специальное значение.

Поэтому литеральный символ `|` необходимо правильно экранировать в строке Java.

После разделения:

```text
logParts.length → 6
```

## 4. Этап 3. Проверка количества полей

Создайте переменную:

«формат записи корректен» (`isLogStructureValid`) типа `boolean`.

Она должна быть `true`, если:

```
logParts.length == 6
```

Если количество частей отличается от `6`, выведите:

```text
Invalid log structure.
```

и завершите дальнейшую обработку записи.

## 5. Этап 4. Извлечение полей

Из массива `logParts` получите:

* «код инцидента» (`incidentCode`);
* «уровень события» (`eventLevel`);
* «название сервиса» (`serviceName`);
* «электронная почта» (`email`);
* «путь к файлу журнала» (`logFilePath`);
* «сообщение инцидента» (`incidentMessage`).

Для первых пяти полей удалите пробелы по краям методом:

```
trim()
```

Для сообщения используйте современный метод:

```
strip()
```

После обработки основные значения должны быть:

```text
incidentCode → INC-5042
eventLevel → error
serviceName → auth-service
email → User@Example.com
logFilePath → C:\Logs\auth.log
incidentMessage → Invalid password for "admin"
```

## 6. Этап 5. Нормализация уровня события

Преобразуйте `eventLevel` в верхний регистр методом:

```
toUpperCase()
```

Сохраните результат обратно в `eventLevel`.

После обработки:

```text
eventLevel → ERROR
```

* «длина кода инцидента» (`incidentCodeLength`);

Получите первый символ `incidentCode` методом:

```
charAt()
```

Для основного теста:

```text
firstCodeCharacter → I
```

Перед использованием `charAt(0)` код должен быть непустым.

## 9. Этап 8. Проверка префикса кода

«код имеет правильный префикс» (`hasValidIncidentPrefix`) типа `boolean`.

Проверьте методом:

```

```

```text

```

Для основного теста:


## 10. Этап 9. Посимвольный анализ кода

«символы кода» (`incidentCodeCharacters`) типа:

```

```

```
toCharArray()
```

Создайте переменную:

«количество цифр в коде» (`digitCount`) типа `int`.

Циклом пройдите по массиву символов.

Символ считайте цифрой, если он находится в диапазоне:

```

```

Для:

```text
INC-5042
```

ожидается:

```text
digitCount → 4
```

## 11. Этап 10. Поиск домена электронной почты

```text

```

«индекс символа @» (`atIndex`).

После этого создайте:

«домен электронной почты» (`emailDomain`).

С помощью:

Полученный домен преобразуйте в нижний регистр.

Для основного теста:

```text

```

Перед вызовом `substring()` убедитесь, что `indexOf()` не вернул:


## 15. Этап 14. Проверка пути к журналу

Непосредственно в коде создайте строку:

«ожидаемый каталог журналов» (`expectedLogDirectory`).

Она должна представлять путь:

```text
C:\Logs\
```

При записи строкового литерала правильно экранируйте обратные слеши (`\`).

Создайте:

* `isExpectedLogDirectory`;
* `isLogFile`.

Обе переменные имеют тип `boolean`.

Первая должна проверять через:

```
startsWith()
```

что путь начинается с ожидаемого каталога.

Вторая должна проверять через:

```
endsWith()
```

что файл заканчивается расширением:

```text
.log
```

Для основного теста обе переменные должны содержать:

```text
true
```

## 16. Этап 15. Извлечение имени файла

Найдите последний обратный слеш в `logFilePath`.

Используйте:

```

```

«имя файла журнала» (`logFileName`).

Для:

```text
C:\Logs\auth.log
```

результат:

```text
auth.log
```

## 17. Этап 16. Маскирование email

Создайте переменную:

«замаскированный email» (`maskedEmail`).

С помощью метода:

```
replace()
```

замените:

```text
@
```

на:

```text
[at]
```

Для основного теста:

```text
maskedEmail → User[at]Example.com
```

После этой операции исходная переменная:

```
email
```

должна по-прежнему содержать:

```text
User@Example.com
```

Вы должны увидеть, что `String` является неизменяемым (`immutable`): метод возвращает новую строку.

## 18. Этап 17. Лексикографическое сравнение сервисов

Создайте строку:

«эталонное имя сервиса» (`referenceServiceName`):

```text
billing-service
```

Создайте:

«результат сравнения сервисов» (`serviceComparison`) типа `int`.

Выполните:

```
serviceName.compareTo(referenceServiceName)
```

После этого создайте:

«положение сервиса» (`serviceOrder`) типа `String`.

Значение:

* `"BEFORE"`, если результат `< 0`;
* `"SAME"`, если результат `== 0`;
* `"AFTER"`, если результат `> 0`.

Для:

```text
auth-service
billing-service
```

ожидается:

```text
serviceOrder → BEFORE
```

Здесь сравнение используется как диагностическая имитация алфавитной сортировки сервисов.

## 19. Этап 18. Подсчёт успешно пройденных проверок

Создайте переменную:

«количество пройденных проверок» (`passedValidationChecks`) типа `int` со значением `0`.

Учитывайте пять проверок:

1. `hasValidIncidentPrefix`;
2. `isRegisteredEmail`;
3. `isErrorEvent`;
4. `isExpectedLogDirectory && isLogFile`;
5. `containsPasswordKeyword`.

Для каждой успешно пройденной проверки увеличивайте счётчик.

Для основного теста:

```text
passedValidationChecks → 5
```

Создайте:

«общее количество проверок» (`totalValidationChecks`):

```text
5
```

## 20. Этап 19. Процент успешных проверок

Создайте:

«процент успешных проверок» (`validationPercent`) типа `double`.

Рассчитайте:

```
passedValidationChecks / totalValidationChecks * 100
```

без потери дробной части.

Для основного теста:

```text
validationPercent → 100.0
```

## 21. Этап 20. `String.format` и локаль

Подключите:

```
Locale
```

Создайте строку:

«форматированный результат проверки» (`formattedValidationResult`).

Используйте:

```
String.format()
```

с локалью:

```
Locale.GERMANY
```

Результат должен выглядеть:

```text
Validation: 100,0%
```

Используйте:

* формат дробного числа с одним знаком;
* `%%` для вывода символа `%`.

При другом значении, например `80.0`, строка должна выглядеть:

```text
Validation: 80,0%
```

## 22. Этап 21. Форматированная строка таблицы

Через `String.format()` создайте:

«строка таблицы» (`formattedTableRow`).

Она должна содержать:

```text
Service         | Level   | File
auth-service    | ERROR   | auth.log
```

Используйте ширину полей и выравнивание.

Требования:

* название сервиса — выравнивание влево;
* уровень — выравнивание влево;
* имя файла — выравнивание влево.

Конкретные размеры полей выберите так, чтобы результат образовывал читаемые колонки.

## 23. Этап 22. Экранированное диагностическое сообщение

Создайте строку:

«диагностическое сообщение» (`escapedDiagnosticMessage`).

Она должна содержать:

* перенос строки через `\n`;
* табуляцию через `\t`;
* двойные кавычки внутри строки через `\"`.

Результат должен выглядеть примерно так:

```text
Source:	"C:\Logs\auth.log"
Level:	"ERROR"
```

Для пути используйте значение переменной `logFilePath`.

## 24. Этап 23. Unicode-символ

Создайте строку:

«значок предупреждения» (`warningSymbol`).

Получите символ:

```text

```

через Unicode escape-последовательность.

Не вставляйте символ предупреждения непосредственно в строковый литерал.

В дальнейшем этот символ будет добавлен в критический отчёт.

## 25. Этап 24. Текстовый блок

Создайте строку:

«баннер отчёта» (`reportBanner`) с помощью текстового блока (`text block`).

Используйте тройные двойные кавычки:

```

...
"""
```

Содержимое:

```text

```

Не создавайте этот баннер через несколько конкатенаций с `\n`.

Цель этапа — закрепить многострочный строковый литерал.

## 26. Этап 25. Метод построения отчёта

Создайте отдельный статический метод:

«построить отчёт инцидента» (`buildIncidentReport`).

Метод должен принимать необходимые обработанные значения и возвращать:

```
String
```

Для сборки текста внутри метода используйте:

```
StringBuilder
```

Не собирайте длинный отчёт последовательностью:

```
result = result + ...
```

## 27. Этап 26. Создание `StringBuilder`

В `buildIncidentReport` создайте:

«построитель отчёта» (`reportBuilder`).

Начальное содержимое:

```text

```

После него должен находиться перенос строки.

## 28. Этап 27. `replace()` у `StringBuilder`

После завершения проверок замените слово:

```text

```

на:

```text

```

если все проверки пройдены.

Если пройдены не все проверки, замените его на:

```text
REVIEW
```

Для изменения существующего содержимого используйте:

```
StringBuilder.replace()
```

Начальный индекс вычислите через длину строки:

```
"STATUS: "
```

Конечный индекс определите на основании длины слова:

```
"PENDING"
```

Не используйте необъяснимые числовые индексы.

## 31. Этап 30. `delete()`

В диагностических целях временно добавьте в конец построителя строку:

```text
TEMPORARY LINE
```

Перед добавлением сохраните текущую длину `reportBuilder` в переменную:

«начало временной строки» (`temporaryLineStart`).

После добавления удалите весь временный фрагмент методом:

```
delete()
```

Используйте:

* сохранённый начальный индекс;
* текущую длину построителя как конечный индекс.


Это упражнение должно показать редактирование уже существующего `StringBuilder`.

## 32. Этап 31. Преобразование `StringBuilder` в `String`

```

```

Метод должен возвращать именно `String`, а не `StringBuilder`.

## 33. Этап 32. Зеркальный код инцидента

Создайте отдельный метод:

«развернуть код инцидента» (`reverseIncidentCode`).

Метод принимает:

```
String incidentCode
```

и возвращает:

```
String
```

Внутри:

1. создайте новый `StringBuilder` на основе `incidentCode`;
2. вызовите `reverse()`;
3. преобразуйте результат через `toString()`;
4. верните строку.

Для:

```text
INC-5042
```

ожидается:

```text
2405-CNI
```

Этот этап является диагностическим упражнением на `reverse()` и не является частью обычной логики
обработки журнала.

## 34. Этап 33. Сравнение содержимого двух `StringBuilder`

Создайте два отдельных объекта `StringBuilder`, содержащих одинаковый текст:

```text

```

Не используйте результат:

```
builderOne.equals(builderTwo)
```

как проверку равенства содержимого.

Преобразуйте оба объекта в `String` через:

```
toString()
```

и сравните полученные строки методом:

```

```

Результат должен быть:

```text
true
```

Вы должны понимать, почему два `StringBuilder` нельзя сравнивать по текстовому содержимому обычным
вызовом `equals()` между самими построителями.

## 49. Требования к `String`

После выполнения задания вы должны понимать, что объект `String` является неизменяемым
(`immutable`).

Методы:

```
trim()
strip()
toLowerCase()
toUpperCase()
replace()
substring()
```

не изменяют существующий объект строки.

Они возвращают результат, который необходимо сохранить или использовать.

## 50. Требования к индексам строки

Перед использованием:

```
charAt()
substring()
```

необходимо учитывать допустимые границы строки.

Перед использованием результата `indexOf()` или `lastIndexOf()` как части индекса проверяйте, найден
ли символ.

Значение:

```text
-1
```

означает, что искомого элемента нет.

## 51. Требования к сравнению строк

Для содержимого строк используйте:

```
equals()
equalsIgnoreCase()
compareTo()
```

в зависимости от требуемой логики.

Не используйте:

```
==
```

для проверки одинакового текстового содержимого двух строк.

## 52. Требования к `StringBuilder`

`StringBuilder` используйте там, где одна строка последовательно изменяется много раз.

Основной отчёт должен собираться через один объект `StringBuilder`.

После завершения обработки преобразуйте его в `String` через:

```
toString()
```

Для пары простых соединений строк использование обычной конкатенации `+` допустимо.

## 53. Что должно быть понято после выполнения

Вы должны уметь объяснить различия между:

```
String
StringBuilder
```

и понимать, почему один неизменяемый, а второй изменяемый.

Вы должны различать:

```
equals()
equalsIgnoreCase()
compareTo()
```

и выбирать способ сравнения в зависимости от задачи.

Вы должны понимать:

```text
indexOf() → индекс или -1
substring(start, end) → end не включается
charAt(index) → один char
split() → String[]
toCharArray() → char[]
```

Вы должны понимать разницу между:

```text
формированием текста
```

и:

```text
форматированием текста
```

и использовать `String.format()` для структурированного представления значений.

## 54. Критерии выполнения

Задание выполнено правильно, если:

1. программа компилируется и запускается;
2. запись журнала считывается одной строкой;
3. строка разделяется на шесть частей через `split()`;
4. литеральный `|` корректно экранируется для `split()`;
5. количество полученных полей проверяется до обращения по индексам;
6. поля очищаются через `trim()` и `strip()`;
7. уровень события нормализуется через `toUpperCase()`;
8. длина строк определяется через `length()`;
9. отдельный символ извлекается через `charAt()`;
10. код преобразуется в `char[]`;
11. количество цифр определяется посимвольно;
12. `indexOf()` используется для поиска `@`;
13. `substring()` извлекает домен;
14. отсутствие `@` не приводит к некорректному `substring()`;
15. email сравнивается через `equalsIgnoreCase()`;
16. уровень события сравнивается через `equals()`;
17. сообщение проверяется через `contains()`;
18. путь проверяется через `startsWith()` и `endsWith()`;
19. имя файла извлекается через `lastIndexOf()` и `substring()`;
20. email маскируется через `replace()`;
21. исходный `email` после `replace()` не изменяется;
22. сервисы сравниваются через `compareTo()`;
23. процент проверок рассчитывается как `double`;
24. процент форматируется с помощью `String.format()` и `Locale.GERMANY`;
25. символ `%` выводится через `%%`;
26. таблица создаётся с использованием ширины и выравнивания полей;
27. используются `\n`, `\t`, `\"` и `\\`;
28. Unicode-символ создаётся escape-последовательностью;
29. многострочный баннер создаётся текстовым блоком;
30. основной отчёт собирается через `StringBuilder`;
31. `append()` добавляет новые фрагменты;
32. `insert()` добавляет критическую пометку в начало;
33. `replace()` изменяет статус внутри построителя;
34. `delete()` удаляет временную строку;
35. `reverse()` используется для диагностического разворота кода;
36. итоговый `StringBuilder` преобразуется в `String`;
37. содержимое двух построителей сравнивается после `toString()`;
38. основной и дополнительные тесты дают ожидаемое поведение;
39. вы можете объяснить неизменяемость `String`;
40. вы можете объяснить, когда следует использовать `StringBuilder` вместо последовательной
    конкатенации `String`.
