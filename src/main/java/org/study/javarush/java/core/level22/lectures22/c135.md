Immutability — неизменяемость record-классов

## 1. Record-классы и неизменяемость

**Неизменяемость** — это свойство объекта, при котором его *состояние* не может быть
изменено после создания. Другими словами: если объект создан, вы не можете поменять
его внутренние данные. Всё! Как в камне высечено.

Представьте билет на поезд. Как только он напечатан, вы не можете изменить дату или
место отправления (ну, если не брать в расчёт хитрые махинации с фотошопом).
Билет — неизменяемый объект. Если вы хотите другой билет — покупаете новый.

В программировании такие объекты называют **immutable objects**. Они защищают
программу от случайных изменений, делают код более безопасным и предсказуемым.

### Признаки неизменяемого объекта

* Все поля объекта — `final` (их можно присвоить только один раз, обычно в конструкторе).
* Нет сеттеров, изменяющих состояние.
* Методы, возвращающие внутренние данные, либо возвращают копии, либо сами данные неизменяемы.

Record-классы в Java помогают создавать структуры данных с **неизменяемыми компонентами**
просто и без боли. Но это только *поверхностная неизменяемость*: если компонент содержит
ссылку на изменяемый объект, содержимое этого объекта по-прежнему можно изменить.

### Почему `record` считается неизменяемым?

**Все компоненты `record` — `final`.**

Когда вы объявляете `record`, компилятор автоматически создаёт поля `private final`.
Это значит, что после создания объекта вы не сможете присвоить им новые значения.

**Нет автоматически созданных сеттеров.**

Record-класс не предоставляет сеттеры, изменяющие компоненты. Написать метод с именем
`setX(int x)` можно, но изменить через него поле `x` компилятор не позволит.

**Конструктор присваивает значения только один раз.**

Значения компонентов устанавливаются при создании объекта. При этом они могут быть
ссылками на изменяемые объекты.

Пример:

```
// Point.java
public record Point(int x, int y) {}
```

```
Point p = new Point(5, 10);
// p.x = 7;  // Ошибка компиляции: поле x закрыто (private) и является final
// p.x(7);   // Ошибка компиляции: нет метода x(int)
System.out.println(p.x()); // 5
```

Попытка изменить компонент или вызвать несуществующий сеттер приводит к ошибке
компиляции. Java строго следит за невозможностью переназначить поля компонентов.

## 2. Преимущества неизменяемых объектов

### Безопасность в многопоточности

В многопоточных программах неизменяемые объекты — это как бронежилет. Если объект
нельзя изменить, разные потоки могут его читать, не боясь изменения данных прямо
во время чтения. При корректной передаче объекта между потоками для чтения его
неизменяемого состояния не требуется дополнительная синхронизация.

Важно: это преимущество относится к **глубоко неизменяемым** объектам. Один лишь
`record` с изменяемым массивом или списком такой гарантии не даёт.

Факт: многие классы в стандартной библиотеке Java, используемые в многопоточных
сценариях, либо неизменяемы, либо специально защищены от изменений.

### Упрощение понимания кода

Если объект неизменяем, вы уверены: передали его в другой метод или класс — и он
не изменится «за вашей спиной». Это облегчает чтение и отладку кода.

### Удобно использовать как ключи в коллекциях

Неизменяемые объекты отлично подходят для использования в качестве ключей в `HashMap`
или элементов `HashSet`. Почему? Потому что результаты `equals()` и `hashCode()`
не меняются вслед за состоянием объекта. Значит, объект не «потеряется» в коллекции.

У `record` с изменяемыми компонентами это преимущество не гарантировано:
например, изменение содержимого списка может изменить результат `hashCode()`.

### Меньше скрытых багов

Изменяемый объект легко испортить, случайно передав ссылку не туда. Неизменяемый же
объект — как печатная книга: никто не может вырвать или переписать страницу.

## 3. Сравнение с обычными классами

Давайте сравним поведение обычного класса и record-класса. Для примера возьмём
простую модель точки на плоскости.

### Обычный класс (mutable)

```
// PointClass.java
public class PointClass {
    private int x;
    private int y;

    public PointClass(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public int getX() {
        return x;
    }

    public int getY() {
        return y;
    }

    public void setX(int x) {
        this.x = x;
    }

    public void setY(int y) {
        this.y = y;
    }
}
```

Можно создать объект и потом сколько угодно менять его состояние:

```
PointClass p = new PointClass(1, 2);
p.setX(10); // Теперь p.getX() вернёт 10
```

### Record-класс (поверхностно immutable)

```
// Point.java
public record Point(int x, int y) {}
```

Создаёте объект — и его компоненты уже нельзя изменить:

```
Point p = new Point(1, 2);
// p.x = 10;  // Ошибка! Нет доступа к полю, и оно final
// p.x(10);   // Ошибка! Нет метода x(int)
```

### Таблица: сравнение поведения

| Особенность       | Обычный класс         | Record-класс                     |
|-------------------|-----------------------|----------------------------------|
| **Поля**          | Могут быть любыми     | Компоненты `private final`       |
| **Сеттеры**       | Можно добавить        | Нельзя изменять компоненты       |
| **Изменяемость**  | Зависит от реализации | Поверхностная неизменяемость     |
| **Автогенерация** | Нет                   | `equals`, `hashCode`, `toString` |

Обычный класс тоже можно сделать полностью неизменяемым. А `record` с изменяемым
компонентом не становится глубоко неизменяемым автоматически.

## 4. Практика: как использовать неизменяемость record-классов

Давайте попробуем применить `record` в небольшом примере. Пусть в банковском
приложении нужно хранить информацию о транзакции:

```
// Transaction.java
public record Transaction(String fromAccount, String toAccount, double amount) {}
```

Создаём объект:

```
Transaction t = new Transaction("12345", "67890", 1500.0);
System.out.println(t);
// Transaction[fromAccount=12345, toAccount=67890, amount=1500.0]
```

Попробуем «перевести» деньги на другой счёт:

```
// t.toAccount = "11111";  // Ошибка! Поле private final
// t.toAccount("11111");   // Ошибка! Нет метода toAccount(String)
```

Если нам нужна другая транзакция — создаём новый объект:

```
Transaction t2 = new Transaction(t.fromAccount(), "11111", t.amount());
```

Важно: неизменяемость не значит «неудобно». Это просто другой стиль работы:
если нужно новое состояние — создаём новый объект.

## 5. Особенности неизменяемости: что нужно помнить

### Неизменяемость — не всегда абсолютна!

Record-класс гарантирует, что его поля нельзя переназначить. Но если поле — ссылка
на изменяемый объект (например, массив или обычный класс), то его содержимое
можно изменить.

### Пример с массивом

```
// DataHolder.java
public record DataHolder(int[] data) {}
```

```
int[] arr = {1, 2, 3};
DataHolder holder = new DataHolder(arr);
arr[0] = 99;
System.out.println(holder.data()[0]); // 99! Массив изменился
```

Вывод: если хотите настоящую неизменяемость, используйте неизменяемые типы (`String`,
`Integer`, другие глубоко неизменяемые record-классы и т. д.) или делайте защитные
копии изменяемых объектов.

Например, для массива можно использовать `Arrays.copyOf()`:

```
int[] copy = Arrays.copyOf(data, data.length);
```

Но копии только в конструкторе недостаточно: автоматически созданный метод `data()`
по-прежнему возвращал бы ссылку на внутренний массив. Для полноценной защиты
нужна копия и при создании, и при получении массива:

```
// DataHolder.java — альтернативная безопасная реализация
import java.util.Arrays;

public record DataHolder(int[] data) {
    public DataHolder {
        data = Arrays.copyOf(data, data.length);
    }

    @Override
    public int[] data() {
        return Arrays.copyOf(data, data.length);
    }
}
```

Для списков подходит `List.copyOf()`: он создаёт неизменяемую копию структуры списка.
`Collections.unmodifiableList()` возвращает представление списка без операций
изменения через него, но исходный список может меняться через другие ссылки.

## 6. Как самому сделать обычный класс неизменяемым

Если вы хотите сделать обычный класс immutable (неизменяемым), придётся вручную:

* Пометить все поля как `private final`.
* Не добавлять сеттеров, изменяющих состояние.
* Все поля инициализировать через конструктор.
* Если поле — изменяемый объект, делать защитную копию (*defensive copy*) при передаче
  в конструктор и при возврате из методов доступа.

Пример:

```
// User.java
public final class User {
    private final String name;
    private final int age;

    public User(String name, int age) {
        this.name = name;
        this.age = age;
    }

    public String name() {
        return name;
    }

    public int age() {
        return age;
    }
}
```

Согласитесь, с record-классом это делается проще и короче:

```
// User.java — альтернативная реализация
public record User(String name, int age) {}
```

## 7. Типичные ошибки при работе с неизменяемыми record-классами

### Ошибка № 1. Попытка изменить поле после создания

Новички часто пытаются написать `p.x = 42;` или `p.x(42);` для record-объекта.
Но компилятор сразу скажет: «Так нельзя! Поле `private final`, а метода `x(int)` нет».

### Ошибка № 2. Использование изменяемых объектов как компонентов `record`

Если вы добавили в `record` компонент типа `List`, `Map`, массив или другой изменяемый
объект, сам `record` не защитит вас от изменения содержимого. Например, для
`record User(List<String> hobbies)` кто-то может добавить или удалить элемент списка.
Это изменит доступное через `record` состояние объекта.

Чтобы этого избежать, используйте неизменяемые коллекции (`List.copyOf()`) или
защитные копии. Помните, что `Collections.unmodifiableList()` сам по себе не создаёт
независимую копию исходного списка.

### Ошибка № 3. Неверное понимание неизменяемости

Некоторые думают, что если объект — `record`, то он защищён от любых изменений.
На самом деле, если компоненты — ссылки на изменяемые объекты, их содержимое
можно поменять, и это приведёт к неожиданным багам.
