Ошибки с модификаторами доступа

## 1. Введение

В Java модификаторы доступа — это как система замков в доме. Они определяют,
кто и откуда может «зайти» к вам в комнату (или к полю/методу вашего класса).
Если все двери открыты — любой может прийти и что-то поменять. Если всё закрыто —
никто не сможет ничего сломать, но и вы сами в какой-то момент можете оказаться
взаперти.

Напомним, в Java есть четыре основных уровня доступа:

| Модификатор         | Свой класс | Тот же пакет | Подкласс вне пакета | Другой пакет |
|---------------------|------------|--------------|---------------------|--------------|
| `private`           | Да         | Нет          | Нет                 | Нет          |
| *(package-private)* | Да         | Да           | Нет                 | Нет          |
| `protected`         | Да         | Да           | Да, с ограничениями | Нет          |
| `public`            | Да         | Да           | Да                  | Да           |

*Package-private* — доступ по умолчанию, когда модификатор не указан явно.
Такой член класса доступен только в пределах своего пакета. Для `protected`
действуют дополнительные правила доступа из подкласса, находящегося в другом пакете.

## 2. Типичные ошибки с модификаторами доступа

### Ошибка № 1. Поля и методы с доступом по умолчанию (`package-private`)

Самая частая ошибка новичков — забыть указать модификатор доступа. В результате
поле или метод становится доступным во всём пакете, хотя вы этого не планировали.
Это может привести к тому, что другой класс (в том же пакете, но не связанный
с вашим) сможет изменить внутреннее состояние вашего объекта.

```
// User.java
// Ошибка проектирования: поле name не скрыто!
class User {
    String name; // package-private!
}
```

В результате любой класс из этого пакета может написать:

```
User user = new User();
user.name = "Вася"; // Без ограничений!
```

Сам по себе `package-private` не является ошибкой: его следует использовать,
когда доступ внутри пакета действительно нужен.

### Ошибка № 2. Нарушение инкапсуляции — открытые поля (`public`)

Вторая по популярности ошибка — объявлять поля класса как `public`.
Это удобно, когда вы только учитесь или пишете короткий пример, но в реальных
проектах часто нежелательно. Вы теряете контроль над тем, кто и как меняет данные.

```
// Account.java
public class Account {
    public double balance; // ОПАСНО!
}
```

Теперь любой код может сделать:

```
Account acc = new Account();
acc.balance = -1000000; // И кто теперь виноват?
```

### Ошибка № 3. Отсутствие геттеров и сеттеров

Иногда разработчик делает поля `private`, но забывает добавить методы для управления
ими. В результате получить или изменить значение невозможно даже там, где это
было бы уместно.

```
// Product.java
public class Product {
    private String name;
    // Нет ни getName(), ни setName()
}
```

Однако геттеры и сеттеры нужны не для каждого поля. Если внешний доступ
не требуется, отсутствие таких методов — правильное ограничение.

### Ошибка № 4. Попытка доступа к `private`-членам из другого класса

Если вы объявили поле или метод как `private`, к нему нельзя обращаться напрямую
из произвольного другого класса, даже если он находится в том же пакете.
Новички часто удивляются, почему код «не видит» поле.

```
// User.java
public class User {
    private String password;
}
```

```
// UserService.java
public class UserService {
    public void resetPassword(User user) {
        // user.password = "123"; // Ошибка компиляции!
    }
}
```

### Ошибка № 5. Ошибки с `protected`

Многие считают, что `protected` означает «видно везде, где есть наследование».
Но в Java доступ к `protected`-членам из другого пакета возможен только
в контексте подкласса, причём есть ограничения на ссылку, через которую
осуществляется обращение.

```
// animals/Animal.java
package animals;

public class Animal {
    protected void sleep() {}
}
```

```
// zoo/Dog.java
package zoo;

import animals.Animal;

public class Dog extends Animal {
    public void test() {
        sleep(); // ОК — вызов унаследованного метода.
    }
}
```

```
// zoo/NotADog.java
package zoo;

import animals.Animal;

public class NotADog {
    public void test() {
        Animal a = new Animal();
        // a.sleep(); // Ошибка: NotADog не является подклассом Animal!
    }
}
```

Вне пакета `animals` подкласс `Dog` может обратиться к `sleep()` через `this`
или ссылку типа `Dog` (либо его подкласса), но не через произвольную ссылку
типа `Animal`. Классу `NotADog` наследование вообще не предоставляет доступа.

## 3. Как правильно: Best practices

### Правило 1: по умолчанию делайте поля `private`

Это главный принцип инкапсуляции. Поля стоит скрывать от внешнего кода.
Если нужно предоставить доступ — используйте геттеры и, при необходимости,
сеттеры.

```
// Book.java
public class Book {
    private String title;
    private int pages;

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }
}
```

### Правило 2: открывайте только необходимые методы

Если метод должен быть доступен извне — делайте его `public`.
Если нужен только внутри пакета — оставляйте `package-private`.
Если метод предназначен для наследников, можно использовать `protected`,
помня, что он также доступен всем классам того же пакета.

### Правило 3: минимизируйте область видимости

Чем меньше область видимости, тем меньше вероятность случайных ошибок
и «неожиданных гостей». Не делайте методы и поля `public`, если в этом
нет необходимости.

### Правило 4: используйте геттеры и сеттеры для контроля доступа

Это позволяет добавить дополнительную логику при чтении или записи поля,
например валидацию.

```
// Account.java
public class Account {
    private double balance;

    public void setBalance(double balance) {
        if (balance < 0) {
            throw new IllegalArgumentException("Баланс не может быть отрицательным!");
        }
        this.balance = balance;
    }

    public double getBalance() {
        return balance;
    }
}
```

Это упрощённый учебный пример. Для денежных сумм в реальном приложении обычно
используют `BigDecimal`, а проверка `balance < 0` сама по себе не отклоняет `NaN`.

### Правило 5: не открывайте внутреннюю реализацию

Если у вас есть массив или список как поле, не возвращайте его напрямую
через геттер — возвращайте копию или предоставляйте только нужные методы.

```
// Team.java
import java.util.ArrayList;
import java.util.List;

public class Team {
    private List<String> members = new ArrayList<>();

    // Правильно:
    public List<String> getMembers() {
        return new ArrayList<>(members); // Возвращаем копию.
    }
}
```

Копия списка защищает сам внутренний список от изменения через возвращённую
ссылку. Это поверхностное копирование: изменяемые элементы списка, если они
есть, отдельно не копируются.

## 4. Примеры на практике

Допустим, у нас есть класс `LibraryUser`, который описывает пользователя библиотеки.

### Пример неправильной реализации

```
// LibraryUser.java — неудачный вариант
public class LibraryUser {
    public String name;
    public int borrowedBooks;
}
```

В таком виде любой код может сделать с объектом всё, что угодно:

```
LibraryUser user = new LibraryUser();
user.name = null;
user.borrowedBooks = -10; // Логика? Какая логика?
```

### Пример правильной реализации с инкапсуляцией

```
// LibraryUser.java — исправленный вариант
public class LibraryUser {
    private String name;
    private int borrowedBooks;

    public LibraryUser(String name) {
        this.name = name;
        this.borrowedBooks = 0;
    }

    public String getName() {
        return name;
    }

    public int getBorrowedBooks() {
        return borrowedBooks;
    }

    public void borrowBook() {
        borrowedBooks++;
    }

    public void returnBook() {
        if (borrowedBooks > 0) {
            borrowedBooks--;
        }
    }
}
```

Теперь внешний код не может напрямую изменить количество взятых книг
или имя пользователя. Всё контролируется только через методы класса.

## 5. Особенности и нюансы реализации

Иногда кажется, что проще сделать поле `public`, чем писать кучу геттеров
и сеттеров. Но это ловушка! Открытое поле — это как открытая дверь в квартиру:
да, удобно, но не очень безопасно.

Ещё одна тонкость — не всегда нужно делать геттеры и сеттеры для всех полей.
Если значение поля не должно меняться после создания объекта, делайте
только геттер, а поле — `final`:

```
// Passport.java
public class Passport {
    private final String number;

    public Passport(String number) {
        this.number = number;
    }

    public String getNumber() {
        return number;
    }
}
```

Также помните: если верхнеуровневый класс объявлен как `public`, имя файла
должно совпадать с именем класса! Это не совсем про модификаторы доступа,
но очень частая ошибка новичков.

## 6. Типичные ошибки при работе с модификаторами доступа

### Ошибка № 1. Забыли указать модификатор доступа у поля или метода

В результате поле или метод становится доступным во всём пакете, даже если вы
этого не хотели. Выбирайте модификатор осознанно: `package-private` не имеет
отдельного ключевого слова и может быть подходящим уровнем доступа.

### Ошибка № 2. Все поля объявлены как `public`

Это нарушает инкапсуляцию, делает код уязвимым к неконтролируемым изменениям.
Привычка из примеров «для простоты» не должна автоматически попадать
в рабочий код.

### Ошибка № 3. Попытка обратиться к `private`-полю из другого класса

Java не позволит сделать это обычным обращением — компилятор вас защитит.
Если захотите обойти ограничение через рефлексию, задумайтесь, почему вообще
возникла такая необходимость.

### Ошибка № 4. Ожидание, что `protected`-члены доступны везде при наследовании

Вне пакета к таким членам можно обратиться из подкласса через `this`, `super`
или ссылку на объект типа самого подкласса (либо его наследника).
Через произвольную ссылку на базовый класс такой доступ не разрешён.

### Ошибка № 5. Возвращение внутренней коллекции через геттер

Если вернуть ссылку на внутренний массив или список, внешний код сможет
изменить его, нарушая инварианты класса.

### Ошибка № 6. Отсутствие контроля при установке значения через сеттер

Если не проверить входящее значение, можно получить некорректное состояние
объекта (например, отрицательный баланс).

### Ошибка № 7. Слишком широкая область видимости методов

Иногда методы делают `public`, хотя они нужны только внутри пакета или класса.
Это открывает лишний API и усложняет поддержку.
