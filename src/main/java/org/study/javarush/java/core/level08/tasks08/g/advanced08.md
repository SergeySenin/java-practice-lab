Задание 08. Система обработки обращений техподдержки (Support Desk System)

Программа принимает обращение, нормализует заголовок, определяет приоритет, обрабатывает статистику
и формирует отчёт. Главная цель — разделить работу на методы с понятной ответственностью.

## 1. Структура и порядок реализации

Создайте публичные классы «решение» (`Solution`) и «обращение поддержки» (`SupportRequest`)
в отдельных файлах `Solution.java` и `SupportRequest.java`, в одном пакете задания.

В `Solution` используйте `public static void main(String[] args)`,
где `args` — аргументы командной строки типа `String[]`.
Подключите `java.util.Scanner` и `java.util.Arrays`. В `main` создайте
«консоль» (`console`) типа `Scanner` с источником `System.in`.

Все вспомогательные методы `Solution` ниже объявляйте `public static`.
Методы `SupportRequest` принадлежат отдельному объекту: не добавляйте им `static`.
Имена, типы и порядок параметров указаны в соответствующих этапах.
Параметр — переменная в объявлении метода; аргумент — передаваемое при вызове значение.

`main` координирует ввод, создание массивов и объектов, вызовы методов и диагностический вывод.
Вычисления выполняйте в указанных методах, не повторяйте их алгоритмы в `main`.
Метод должен отвечать за одно действие; сохраняйте предложенные содержательные имена.

Для вывода используйте `System.out.println`, для массивов — `Arrays.toString`.
Подставляйте значения в образцы, сохраняя пробелы внутри строковых литералов.
Обозначения в квадратных скобках в шаблонах отчётов заменяйте соответствующими значениями.

## 2. Этап 1. Статистика работы системы

За пределами методов `Solution` объявите «количество обработанных обращений»
(`processedRequestCount`): поле `private static int` с начальным значением `0`.

Поле принадлежит классу, а не отдельному вызову метода. Изменяйте его в методе регистрации,
читайте в методе получения счётчика. Из `main` напрямую к нему не обращайтесь.

## 3. Этап 2. Ввод обращения

Считайте «исходный заголовок обращения» (`requestTitleInput`) типа `String` через `nextLine()`.
Затем через `nextInt()` получите четыре переменные типа `int` в указанном порядке:

* «идентификатор обращения» (`requestId`);
* «серьёзность проблемы» (`severityLevel`);
* «количество затронутых пользователей» (`affectedUserCount`);
* «время ожидания в минутах» (`waitingTimeMinutes`).

Основной ввод; пробелы по краям первой строки намеренные:

```text
   Payment service unavailable   
501
4
120
95
```

Серьёзность находится в диапазоне `1–5`. Дополнительная проверка диапазона не требуется.

## 4. Этап 3. Метод нормализации заголовка

Метод «нормализовать заголовок» (`normalizeTitle`) возвращает `String`.
Единственный параметр — `String requestTitleInput`, исходный заголовок.

Удалите пробелы по краям через `trim()` и верните результат через `return`.
Метод ничего не печатает: возврат значения и вывод — разные действия.
В `main` сохраните результат в «заголовок обращения» (`requestTitle`) типа `String`.

Для основного ввода получится `Payment service unavailable`.

## 5. Этап 4. Метод расчёта приоритета

Метод «рассчитать приоритет» (`calculatePriority`) возвращает `int` и принимает по порядку
`int severityLevel`, `int affectedUserCount`, `int waitingTimeMinutes`
с теми же значениями, что на этапе ввода.

Проверяйте условия последовательно:

1. Верните `3`, если `severityLevel >= 4` или `affectedUserCount >= 100`.
2. Иначе верните `2`, если `severityLevel >= 2` или `waitingTimeMinutes >= 60`.
3. В остальных случаях верните `1`.

Все пути должны возвращать значение. После безусловного `return` не размещайте действия,
которые должны выполниться. В `main` сохраните результат в «уровень приоритета»
(`priorityLevel`) типа `int`. Для основного теста он равен `3`.

## 6. Этап 5. Метод проверки обращения

Метод «можно принять обращение» (`canAcceptRequest`) возвращает `boolean`.
Параметры: `String requestTitle` — заголовок, `int priorityLevel` — приоритет.

Верните логическое выражение: заголовок непустой и приоритет от `1` до `3` включительно.
Не выводите результат внутри метода. Сохраните его в `main` в «обращение принято»
(`isRequestAccepted`) типа `boolean`. Для основного теста ожидается `true`.

## 7. Этап 6. Досрочный `return` в `void`-методе

Метод «вывести критическое предупреждение» (`printCriticalWarning`) возвращает `void`.
Параметры: `int priorityLevel` — приоритет, `String requestTitle` — заголовок.

Если приоритет не равен `3`, сразу выполните `return;` и ничего не печатайте.
Иначе выведите префикс `"CRITICAL REQUEST: "` и переданный заголовок:

```text
CRITICAL REQUEST: Payment service unavailable
```

Вызовите метод из `main` после проверки обращения. Здесь `return;` завершает метод,
не возвращая значение.

## 8. Этап 7. Метод регистрации обработанного обращения

Метод «зарегистрировать обработанное обращение» (`registerProcessedRequest`)
возвращает `void` и принимает `boolean isRequestAccepted` — признак принятия.

При `false` используйте ранний `return;`. Иначе увеличьте `processedRequestCount` на единицу.
Вызовите метод один раз: для основного теста счётчик станет равен `1`.

## 9. Этап 8. Метод получения счётчика

Метод «получить количество обработанных обращений» (`getProcessedRequestCount`)
не принимает параметров и возвращает `int` — текущее поле `processedRequestCount`.

В `main` сохраните результат в «текущее количество обработанных обращений»
(`currentProcessedRequestCount`) типа `int`. Используйте его в итоговом отчёте.

## 10. Этап 9. Массив нагрузки

В `main` быстрой инициализацией создайте «количество обращений за предыдущие периоды»
(`historicalRequestCounts`) типа `int[]` со значениями `3, 7, 2, 5`.
Это нагрузка за четыре предыдущих периода.

## 11. Этап 10. Метод расчёта общей нагрузки

Метод «рассчитать общее количество обращений» (`calculateTotalRequestCount`) возвращает `int`.
Параметр `int[] historicalRequestCounts` — массив нагрузки.

Создайте локальную «сумму» (`sum`) типа `int`, первоначально `0`.
Переберите массив циклом `for`: «индекс периода» (`i`) типа `int` изменяется от `0`
до `historicalRequestCounts.length - 1`. Прибавьте каждый элемент к `sum` и верните сумму.

В `main` сохраните результат в «общее количество прошлых обращений»
(`totalHistoricalRequestCount`) типа `int`. Ожидается `17`.
Локальная `sum` существует только внутри метода и недоступна в `main`.

## 12. Этап 11. Массив времени ответа

В `main` создайте «время ответа в минутах» (`responseTimesInMinutes`) типа `int[]`
со значениями `40, 55, 30, 70` — время ответа на четыре обращения.

## 13. Этап 12. Изменение массива внутри метода

Метод «уменьшить время ответа» (`reduceResponseTimes`) возвращает `void`.
Параметры: `int[] responseTimesInMinutes` — массив времени,
`int reductionMinutes` — количество минут уменьшения.

Циклом `for` уменьшите каждый элемент на `reductionMinutes`.
«Индекс времени ответа» (`i`) типа `int` идёт от `0` до длины массива минус один.
Новый массив не создавайте. В `main` передайте уменьшение `5` и выведите массив.

### Дополнительный тест 5. Массив можно изменить через параметр

Ожидаемый переход:

```text
[40, 55, 30, 70]
[35, 50, 25, 65]
```

Объясните, почему изменение элементов переданного объекта видно после возврата в `main`.

## 14. Этап 13. Попытка заменить массив через параметр

Метод «попытаться заменить время ответа» (`tryToReplaceResponseTimes`) возвращает `void`.
Параметр `int[] responseTimesInMinutes` — массив времени ответа.

Присвойте параметру новый массив `new int[] {5, 5, 5, 5}`.
Вызовите метод после уменьшения времени и снова выведите массив из `main`.

### Дополнительный тест 6. Переменную-массив заменить нельзя

Ожидается прежнее содержимое `[35, 50, 25, 65]`.
Сравните изменение `responseTimesInMinutes[0]` и присваивание параметру нового массива.
Параметр получает копию ссылки: новое присваивание меняет только эту локальную копию.

## 15. Этап 14. Правильная замена массива через `return`

Метод «создать новый набор времени ответа» (`createReplacementResponseTimes`)
не принимает параметров и возвращает `int[]` — новый массив `15, 20, 25, 30`.

В `main` присвойте результат переменной `responseTimesInMinutes` и выведите её:
ожидается `[15, 20, 25, 30]`. Теперь заменяется сама переменная вызывающего метода,
поскольку присваивание выполнено в `main`.

## 16. Этап 15. Эксперимент с примитивным типом

В `main` объявите «дневной лимит обращений» (`dailyRequestLimit`) типа `int` со значением `100`.
Метод «попытаться изменить дневной лимит обращений» (`tryToChangeDailyRequestLimit`)
возвращает `void` и принимает `int dailyRequestLimit` — дневной лимит.
Внутри присвойте параметру `999`. Вызовите метод и выведите переменную из `main`.

### Дополнительный тест 4. Примитив передаётся независимо

До вызова и после него `dailyRequestLimit` равен `100`, хотя параметр внутри получил `999`.
Объясните результат: методу передана копия значения `int`.

## 17. Этап 16. Класс обращения `SupportRequest`

Создайте три нестатических поля:

* «идентификатор обращения» (`requestId`) — `public int`;
* «заголовок обращения» (`requestTitle`) — `public String`;
* «уровень приоритета» (`priorityLevel`) — `private int`.

Публичные поля доступны из `Solution`. Приватный приоритет напрямую читать и менять нельзя.

## 18. Этап 17. Метод установки приоритета и `this`

В `SupportRequest` создайте публичный метод «установить уровень приоритета»
(`setPriorityLevel`), возвращающий `void`. Параметр `int priorityLevel` — новый приоритет.

Имя параметра намеренно совпадает с именем поля: это затенение (shadowing).
Присвойте полю текущего объекта через `this.priorityLevel` значение параметра `priorityLevel`.
Объясните, какое имя обозначает поле, а какое — параметр.

## 19. Этап 18. Метод получения приоритета

Публичный метод «получить уровень приоритета» (`getPriorityLevel`)
не принимает параметров и возвращает `int` — приватное поле `priorityLevel`.
Используйте его при передаче приоритета объекта в итоговый отчёт.

## 20. Этап 19. Приватный метод класса обращения

Приватный метод «получить название приоритета» (`getPriorityLabel`)
не принимает параметров и возвращает `String` по полю `priorityLevel`:

* `3` → `"CRITICAL"`;
* `2` → `"MEDIUM"`;
* `1` → `"NORMAL"`;
* любое другое значение → `"UNKNOWN"`.

Из `Solution` этот метод напрямую недоступен.

## 21. Этап 20. Публичный метод вывода карточки обращения

Публичный метод «вывести карточку обращения» (`printRequestProfile`)
не принимает параметров, возвращает `void` и выводит:

```text
ID:             [requestId]
Title:          [requestTitle]
Priority:       [priorityLevel]
Priority label: [результат getPriorityLabel()]
```

Название приоритета получите вызовом `getPriorityLabel()` внутри `SupportRequest`:
метод того же класса имеет доступ к приватному методу.

## 22. Этап 21. Создание объекта обращения

В `main` через `new` создайте «обращение» (`request`) типа `SupportRequest`.
Заполните публичные поля `request.requestId` и `request.requestTitle` из
`requestId` и `requestTitle`. Передайте `priorityLevel` в `request.setPriorityLevel(...)`.

Вызовите `request.printRequestProfile()`.
Методы экземпляра вызываются через объект `request`, методы `Solution` — через класс
или непосредственно из его `main`.

## 23. Этап 22. Практическая проверка `private`

### Диагностический эксперимент 1. Приватное поле

Временно добавьте в `main` строку `request.priorityLevel = 1;`.
Получите ошибку компиляции и объясните отличие `public` от `private` для двух классов.

### Диагностический эксперимент 2. Приватный метод

Отдельно попробуйте вызвать `request.getPriorityLabel();` из `Solution`.
Получите ошибку доступа, хотя вызов внутри `printRequestProfile` разрешён.

После каждого опыта удалите или закомментируйте ошибочную строку и снова скомпилируйте программу.
Не оставляйте неправильные обращения активными.

## 24. Этап 23. Изменение объекта через параметр метода

Метод `Solution` «обновить заголовок обращения» (`updateRequestTitle`) возвращает `void`.
Параметры: `SupportRequest request` — обращение,
`String newRequestTitle` — новый заголовок.

Измените поле `requestTitle` переданного объекта. В `main` передайте `request`
и исходный нормализованный `requestTitle` с добавлением `" - verified"`.
Для основного теста новый заголовок:

```text
Payment service unavailable - verified
```

Снова вызовите `request.printRequestProfile()`: изменение должно быть видно снаружи метода.
При других входных данных дополнение прибавляется к их заголовку.

## 25. Этап 24. Попытка заменить объект через параметр

Метод «попытаться заменить обращение» (`tryToReplaceRequest`) возвращает `void`
и принимает `SupportRequest request` — обращение.

Внутри присвойте параметру новый `SupportRequest`. Заполните его:
`requestId` — `999`, `requestTitle` — `"Another request"`, приоритет через
`setPriorityLevel` — `1`. После вызова в `main` снова выведите карточку исходного `request`.

### Дополнительный тест 7. Объект ведёт себя аналогично массиву

После `updateRequestTitle` меняется поле исходного объекта; после `tryToReplaceRequest`
ссылка в `main` остаётся прежней. Для основного теста остаются идентификатор `501`,
обновлённый заголовок и приоритет `3`. Объясните разницу между изменением объекта
и присваиванием параметру другой ссылки.

## 26. Этап 25. Локальная область видимости

В `main` внутри `if (isRequestAccepted)` объявите «сообщение об обработке обращения»
(`requestProcessingMessage`) типа `String` со значением `"Request accepted for processing"`.
Выведите его внутри этого блока.

### Диагностический эксперимент 3. Область видимости

Временно попробуйте вывести `requestProcessingMessage` после закрывающей скобки блока.
Зафиксируйте ошибку компиляции и удалите или закомментируйте неправильную строку.
Локальная переменная доступна только внутри своей области видимости (scope).

## 27. Этап 26. Формирование итогового отчёта методом

Метод «сформировать отчёт» (`buildRequestSummary`) возвращает `String`.
Параметры в порядке объявления и вызова:

* `int requestId` — идентификатор обращения;
* `String requestTitle` — актуальный заголовок;
* `int priorityLevel` — приоритет;
* `boolean isRequestAccepted` — результат первоначальной проверки;
* `int totalHistoricalRequestCount` — общая прошлая нагрузка;
* `int currentProcessedRequestCount` — текущий счётчик;
* `int dailyRequestLimit` — дневной лимит.

Сформируйте и верните многострочную строку; сам метод ничего не печатает.
Соединяйте фрагменты через `+` и `"\n"`. Поля идут в порядке параметров:

```text
Request ID:            [значение]
Title:                 [значение]
Priority:              [значение]
Accepted:              [true/false]
Total historical load: [значение]
Processed requests:    [значение]
Daily request limit:   [значение]
```

Передавайте идентификатор и заголовок из `request`, приоритет — из `request.getPriorityLevel()`,
остальные значения — из одноимённых переменных `main`.
Добавление `" - verified"` не запускает повторную проверку принятия и не меняет счётчик.

## 28. Этап 27. Метод вывода отчёта

Метод «вывести отчёт об обращении» (`printRequestReport`) возвращает `void`.
Единственный параметр `String report` — отчёт. Выведите переданную строку.

## 29. Этап 28. Передача результата одного метода другому

При итоговом выводе передайте результат `buildRequestSummary(...)` непосредственно
в `printRequestReport(...)`. Промежуточную переменную отчёта в `main` не создавайте.

Один метод возвращает значение, а второй получает его как аргумент.

## 30. Этап 29. Основной порядок работы `main`

Выполняйте действия этапов в их порядке: ввод и проверка обращения, предупреждение и регистрация,
получение счётчика, расчёт нагрузки, эксперименты с массивом и лимитом, создание и изменение
объекта, сообщение о принятии, итоговый отчёт. Диагностический вывод размещайте до отчёта.

Ошибочные строки опытов с доступом и областью видимости в рабочую последовательность не входят.
