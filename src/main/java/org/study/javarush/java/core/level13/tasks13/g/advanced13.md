Задание 13. Планировщик международных релизов (Global Release Scheduler)

Программа помогает координировать выпуск программного обеспечения
между командами в Лондоне, Нью-Йорке и Токио.
Менеджер вводит первоначальное время релиза по Лондону и дату начала подготовки.
Программа переносит начало работ, рассчитывает время для трёх городов,
продолжительность работ и сроки подготовки, затем формирует отчёт.

Отдельная диагностическая программа показывает текущее время, совместимость со старым API дат
и поведение при переходе на летнее время. Используйте Java 17 или Java 21.

## 1. Структура проекта

Создайте два файла в одном пакете задания:

* `Solution.java`        — публичный класс «решение» (`Solution`);
* `TimeDiagnostics.java` — публичный класс «диагностика времени» (`TimeDiagnostics`).

В обоих классах создайте главный метод программы (`main`):

```
public static void main(String[] args)
```

Параметр «аргументы командной строки» (`args`) типа `String[]` здесь не используется.
Классы запускайте независимо: `Solution` выполняет этапы 1–21,
а `TimeDiagnostics` — этапы 22–26 и отдельные диагностические эксперименты.

Для основной программы используйте классы из
`java.time`, `java.time.format`, `java.time.temporal` и `java.util.Scanner`.
Основную логику расписания выполняйте через `java.time`, без `java.util.Date` и `Calendar`.
Для диагностики дополнительно понадобятся `java.util.Date` и `java.util.Locale`.

Все четыре вспомогательных метода `Solution` объявляйте `public static`.
Имена, типы и порядок параметров сохраняйте по соответствующим этапам.
Дополнительные вспомогательные методы не требуются.
Остальные действия выполняйте в `main` соответствующего класса.

Промежуточные образцы и схемы со знаком `→` показывают контрольные значения.
Дополнительно печатать их в основной программе не требуется: её вывод — итоговый отчёт
либо сообщение об ошибке ввода. В диагностике выполняйте указанные команды вывода.
В шаблонах сообщений заменяйте обозначения в квадратных скобках фактическими значениями;
сами скобки и поясняющий текст внутри них не печатайте.

## 2. Этап 1. Ввод исходного расписания

В `Solution.main` создайте «консоль» (`console`) типа `Scanner`, связанную с `System.in`.
Через `nextLine()` последовательно считайте две переменные типа `String`:

1. «Исходное время релиза» (`releaseStartInput`).
2. «Исходную дату начала подготовки» (`planningStartInput`).

Основной ввод:

```text
15.06.2026 14:30
10.04.2026
```

Первое значение — 15 июня 2026 года, 14:30 по местному времени Лондона.
Второе — 10 апреля 2026 года.
Удалите пробелы по краям через `trim()`, сохранив результат обратно в каждую переменную.

Не подменяйте введённые даты результатом `LocalDate.now()`: основной тест должен давать
одинаковый результат независимо от дня запуска.

## 3. Этап 2. Создание форматтеров

Создайте «форматтер даты и времени» (`dateTimeFormatter`) типа `DateTimeFormatter`
через `DateTimeFormatter.ofPattern()` с шаблоном:

```text
dd.MM.uuuu HH:mm
```

Создайте «форматтер даты» (`dateFormatter`) того же типа с шаблоном:

```text
dd.MM.uuuu
```

Для обоих форматтеров включите строгий разбор через `withResolverStyle(ResolverStyle.STRICT)`
и сохраните полученные объекты в соответствующие переменные.
`uuuu` задаёт год напрямую; в сочетании со строгим режимом несуществующая дата
должна приводить к ошибке, а не исправляться автоматически.

Первый форматтер используйте для даты с часами и минутами, второй — только для даты.
Повторно используйте их при разборе строк и форматировании отчёта.

## 4. Этап 3. Метод преобразования времени релиза

Создайте метод «преобразовать время релиза» (`parseReleaseStart`):

```
public static LocalDateTime parseReleaseStart(
        String releaseStartInput,
        DateTimeFormatter dateTimeFormatter)
```

Параметры — «исходное время релиза» (`releaseStartInput`)
и «форматтер даты и времени» (`dateTimeFormatter`).
Преобразуйте строку через `LocalDateTime.parse()` с переданным форматтером
и верните результат через `return`. Сам метод ничего не печатает.

Для основного теста:

```text
2026-06-15T14:30
```

Не перехватывайте `DateTimeParseException` внутри метода:
если преобразование невозможно, исключение передаётся вызывающему коду.

## 5. Этап 4. Метод преобразования даты подготовки

Создайте метод «преобразовать дату подготовки» (`parsePlanningStart`):

```
public static LocalDate parsePlanningStart(
        String planningStartInput,
        DateTimeFormatter dateFormatter)
```

Параметры — «исходная дата начала подготовки» (`planningStartInput`)
и «форматтер даты» (`dateFormatter`).
Преобразуйте строку через `LocalDate.parse()` с переданным форматтером
и верните результат. Метод ничего не печатает и не перехватывает `DateTimeParseException`.

Для основного теста:

```text
2026-04-10
```

В `main` предусмотрите переменные для результатов:

* «первоначальное время релиза» (`originalReleaseStart`) типа `LocalDateTime`;
* «дата начала подготовки» (`planningStartDate`) типа `LocalDate`.

## 6. Этап 5. Обработка ошибок ввода даты

В `main` выполните два последовательных блока `try/catch`.
В первом вызовите `parseReleaseStart()` и присвойте результат `originalReleaseStart`.
Во втором вызовите `parsePlanningStart()` и присвойте результат `planningStartDate`.
Переменные результатов объявите до блоков, чтобы использовать их в следующих этапах.

В каждом обработчике перехватывайте только `DateTimeParseException`
с параметром «исключение» (`exception`).

Сообщение при ошибке первого значения:

```text
Invalid release date-time: [введённая строка]
```

Сообщение при ошибке второго значения:

```text
Invalid planning date: [введённая строка]
```

Подставляйте соответствующую строку после `trim()`.
После сообщения завершайте `main` через `return`.
Если ошибочны обе строки, выводится только сообщение о времени релиза:
до разбора даты подготовки выполнение не доходит.
Расписание и отчёт после ошибки не формируются.
Не используйте общий `catch (Exception exception)`.

## 7. Этап 6. Получение компонентов даты и времени

Из `originalReleaseStart` получите:

* «первоначальную дату релиза» (`releaseDate`)         типа `LocalDate` через `toLocalDate()`;
* «первоначальное время суток» (`originalReleaseTime`) типа `LocalTime` через `toLocalTime()`.

`releaseDate` остаётся первоначальной датой, даже если перенос изменит день начала работ.
По ней определяйте день недели, ISO-дату в отчёте, заморозку изменений
и продолжительность подготовки. Скорректированное расписание рассчитывается отдельно.

Из `releaseDate` получите три переменные типа `int`:

| Переменная     | Назначение          | Метод             |  Результат |
|----------------|---------------------|-------------------|-----------:|
| `releaseYear`  | Год релиза          | `getYear()`       |     `2026` |
| `releaseMonth` | Номер месяца релиза | `getMonthValue()` |        `6` |
| `releaseDay`   | День месяца релиза  | `getDayOfMonth()` |       `15` |

Создайте «день недели первоначального релиза» (`releaseDayOfWeek`) типа `DayOfWeek`
через `getDayOfWeek()`.

Для основного теста:

```text
MONDAY
```

Из `originalReleaseTime` получите «первоначальный час» (`originalReleaseHour`)
и «первоначальную минуту» (`originalReleaseMinute`) типа `int`
через `getHour()` и `getMinute()` соответственно. Ожидаются `14` и `30`.

## 8. Этап 7. Изменение расписания

Менеджер перенёс начало релиза сначала на два часа позже,
затем на 30 минут раньше полученного времени.
Создайте метод «рассчитать скорректированное время релиза» (`calculateAdjustedReleaseStart`):

```
public static LocalDateTime calculateAdjustedReleaseStart(
        LocalDateTime originalReleaseStart)
```

Параметр — «первоначальное время релиза» (`originalReleaseStart`).
Последовательно примените `plusHours(2)` и `minusMinutes(30)`.
Сохраните результат в «скорректированное время релиза» (`adjustedReleaseStart`)
типа `LocalDateTime` и верните его. Метод ничего не печатает.

В `main` вызовите метод и сохраните возвращённое значение
в одноимённую переменную `adjustedReleaseStart` типа `LocalDateTime`.

Контрольные значения:

```text
originalReleaseStart → 2026-06-15T14:30
adjustedReleaseStart → 2026-06-15T16:00
```

`LocalDateTime` неизменяем: исходный объект `originalReleaseStart` должен остаться прежним.
Не используйте `setHours()` или аналогичные методы старых API.
Здесь изменяется местное время до привязки к часовому поясу.

## 9. Этап 8. Проверка времени рабочего дня

Лондонская команда работает с `09:00` до `18:00` включительно.
Через `LocalTime.of()` создайте:

* «начало рабочего дня» (`workingDayStart`) типа `LocalTime` — `09:00`;
* «конец рабочего дня»  (`workingDayEnd`)   типа `LocalTime` — `18:00`.

Из `adjustedReleaseStart` через `toLocalTime()` получите
«скорректированное время суток» (`adjustedReleaseTime`) типа `LocalTime`.

Проверьте, что время не раньше `workingDayStart` и не позже `workingDayEnd`.
Используйте `isBefore()`, `isAfter()` и логические операторы.
Результат сохраните в «начало внутри рабочего дня» (`isStartWithinWorkingHours`)
типа `boolean`. Для основного теста ожидается `true`.

Проверяется только время начала; продолжительность и время окончания учитываются позже.
Отдельную проверку выходных дней не добавляйте.

## 10. Этап 9. Часовые пояса

Через `ZoneId.of()` создайте три переменные типа `ZoneId`:

| Переменная    | Назначение             | Идентификатор зоны  |
|---------------|------------------------|---------------------|
| `londonZone`  | Часовой пояс Лондона   | `Europe/London`     |
| `newYorkZone` | Часовой пояс Нью-Йорка | `America/New_York`  |
| `tokyoZone`   | Часовой пояс Токио     | `Asia/Tokyo`        |

Не задавайте смещения вручную числами вроде `+1`, `-4` или `+9`.
Часовой пояс содержит правила, зависящие от даты, включая переходы на летнее время.

## 11. Этап 10. Привязка локального времени к часовому поясу

Создайте метод «привязать время к часовому поясу» (`attachTimeZone`):

```
public static ZonedDateTime attachTimeZone(
        LocalDateTime localDateTime,
        ZoneId zoneId)
```

Параметры — «локальные дата и время» (`localDateTime`) и «часовой пояс» (`zoneId`).
Примените `atZone()` к переданным дате и времени с переданной зоной и верните результат.
Сам метод ничего не печатает.

В `main` вызовите метод дважды:

1. Для `originalReleaseStart` с `londonZone`.
2. Для `adjustedReleaseStart` с `londonZone`.

Сохраните результаты в:

* «первоначальный релиз в Лондоне»    (`originalReleaseLondon`) типа `ZonedDateTime`;
* «скорректированный релиз в Лондоне» (`adjustedReleaseLondon`) типа `ZonedDateTime`.

Для основного теста:

```text
originalReleaseLondon:
2026-06-15T14:30+01:00[Europe/London]

adjustedReleaseLondon:
2026-06-15T16:00+01:00[Europe/London]
```

Смещение `+01:00` соответствует лондонскому летнему времени в указанную дату.

## 12. Этап 11. Единый момент времени через `Instant`

Преобразуйте `adjustedReleaseLondon` через `toInstant()`
в «абсолютное время начала» (`releaseStartInstant`) типа `Instant`.

Для основного теста:

```text
2026-06-15T15:00:00Z
```

`Instant` обозначает конкретный момент, не привязанный к местному отображению часов.
`Z` обозначает нулевое смещение относительно UTC.
Не получайте `Instant` ручным вычитанием часа из `LocalDateTime`.

## 13. Этап 12. Время релиза в Нью-Йорке и Токио

Из `adjustedReleaseLondon` через `withZoneSameInstant()` с соответствующими зонами получите:

* «начало релиза в Нью-Йорке» (`releaseStartNewYork`) типа `ZonedDateTime`;
* «начало релиза в Токио»     (`releaseStartTokyo`)   типа `ZonedDateTime`.

Контрольные значения:

| Город    | Локальное время релиза  |
|----------|-------------------------|
| Лондон   | 15.06.2026 16:00        |
| Нью-Йорк | 15.06.2026 11:00        |
| Токио    | 16.06.2026 00:00        |

В Токио релиз приходится уже на **следующий календарный день**.
Все три объекта обозначают один и тот же момент времени.

Через `isEqual()` сравните `adjustedReleaseLondon` и `releaseStartNewYork`.
Результат сохраните в «совпадает момент релиза в Нью-Йорке» (`isSameInstantInNewYork`)
типа `boolean`. Для основного теста ожидается `true`.

## 14. Этап 13. Продолжительность релиза

Плановая длительность технических работ — 75 минут.
Через `Duration.ofMinutes(75)` создайте «продолжительность релиза» (`releaseDuration`)
типа `Duration`.

Прибавьте `releaseDuration` к `adjustedReleaseLondon`
и сохраните результат в
«завершение релиза в Лондоне» (`releaseEndLondon`) типа `ZonedDateTime`.

Для основного теста:

```text
2026-06-15T17:15+01:00[Europe/London]
```

Из `releaseEndLondon` через `toInstant()` получите
«абсолютное время завершения» (`releaseEndInstant`) типа `Instant`.

Контрольное значение:

```text
2026-06-15T16:15:00Z
```

## 15. Этап 14. Завершение релиза в других странах

## 16. Этап 15. Разница между первоначальным и новым временем

Через `Duration.between()` для `originalReleaseLondon.toInstant()`
и `releaseStartInstant`, именно в таком порядке,
создайте «продолжительность переноса» (`scheduleShiftDuration`) типа `Duration`.
Через `toMinutes()` получите «перенос в минутах» (`scheduleShiftMinutes`) типа `long`.

Для основного теста:

```text
90
```

Отдельно через `Duration.between()` для `releaseStartInstant` и `releaseEndInstant`
получите длительность работ, затем преобразуйте её в минуты через `toMinutes()`.
Результат сохраните в
«фактическую длительность в минутах» (`releaseDurationMinutes`) типа `long`.

Контрольное значение:

```text
75
```

Перенос начала и длительность самого релиза — разные временные интервалы.
В этапе 7 местные часы сдвигаются на 90 минут до привязки к зоне.
`scheduleShiftMinutes` измеряет расстояние между реальными моментами:
при переходе между сезонными смещениями оно может отличаться от 90 минут.

## 17. Этап 16. Проверка порядка событий

Сравните `releaseStartInstant` и `releaseEndInstant` через `isBefore()` или `isAfter()`.
Сохраните результат в «завершение позже начала» (`isReleaseEndAfterStart`) типа `boolean`.
Для основного теста ожидается `true`.

Не сравнивайте время как строки и не применяйте `>` или `<`
непосредственно к объектам `ZonedDateTime`.

## 18. Этап 17. Дата заморозки изменений

Контрольное значение:

```text
3
```

## 20. Этап 19. Календарный период подготовки

## 23. Этап 22. Текущая дата и время

Перейдите в `TimeDiagnostics.main`. Создайте:

* «текущую дату»         (`currentDate`)     типа `LocalDate`     через `LocalDate.now()`;
* «текущее время»        (`currentTime`)     типа `LocalTime`     через `LocalTime.now()`;
* «текущие дату и время» (`currentDateTime`) типа `LocalDateTime` через `LocalDateTime.now()`;
* «текущий момент»       (`currentInstant`)  типа `Instant`       через `Instant.now()`.

Первые три вызова используют системный часовой пояс; `Instant` представляет момент времени.
Вызовы выполняются отдельно: значения не обязаны соответствовать одному моменту
до долей секунды, а около полуночи может измениться и дата.

Из `currentDate` получите переменные типа `LocalDate`:

* «вчера»             (`yesterday`)    через `minusDays(1)`;
* «завтра»            (`tomorrow`)     через `plusDays(1)`;
* «через десять дней» (`tenDaysLater`) через `plusDays(10)`.

Из `currentTime` получите переменные типа `int`:

* «текущий час»     (`currentHour`)   через `getHour()`;
* «текущую минуту»  (`currentMinute`) через `getMinute()`;
* «текущую секунду» (`currentSecond`) через `getSecond()`.

Вывод:

```text
Current date:      [текущая дата]
Yesterday:         [вчера]
Tomorrow:          [завтра]
Ten days later:    [дата]
Current time:      [текущее время]
Current hour:      [число]
Current minute:    [число]
Current second:    [число]
Current date-time: [дата и время]
Current instant:   [момент UTC]
```

Результаты зависят от системных часов, поэтому фиксированных значений здесь нет.
Все значения определяйте программно, а не задавайте вручную.

## 24. Этап 23. Текущее время в трёх часовых поясах

Через отдельные вызовы `ZonedDateTime.now()` с соответствующей зоной получите:

* «текущее время в Лондоне»   (`currentTimeInLondon`)  типа `ZonedDateTime`;
* «текущее время в Нью-Йорке» (`currentTimeInNewYork`) типа `ZonedDateTime`;
* «текущее время в Токио»     (`currentTimeInTokyo`)   типа `ZonedDateTime`.

Выведите каждое значение на отдельной строке с названием города.
Точное оформление этих трёх строк свободное.
Отдельные вызовы `now()` не обязаны возвращать один и тот же момент.
Нельзя получить `LocalDateTime.now()` и просто приписать название другой страны.

## 25. Этап 24. Совместимость со старым API

Через `Instant.parse()` создайте «исходный момент» (`originalInstant`) типа `Instant`:

Через `Date.from()` преобразуйте его

Затем через `legacyDate.toInstant()`

Сравните `originalInstant` и `restoredInstant` методом `equals()`.
Результат сохраните в
«преобразование сохранило момент» (`isLegacyConversionPreserved`) типа `boolean`.

Вывод:

```text
Legacy conversion preserved instant: true
```

В этом опыте используется точное количество секунд без дробной части.
`java.util.Date` не сохраняет наносекундную точность произвольного `Instant`.

## 28. Диагностические эксперименты

Выполняйте эксперименты по одному в `TimeDiagnostics.main`.
После каждого опыта удаляйте временный код и восстанавливайте рабочую версию диагностики.
Имена временных переменных могут повторяться в разных экспериментах:
одновременно активным должен быть только один опыт.

### Диагностический эксперимент 1. Неизменяемость `LocalDate`

Создайте «исходную дату» (`originalDate`) типа `LocalDate` со значением `2026-06-15`.
Вызовите `plusDays(5)`, не сохраняя результат, и выведите исходную переменную:
она должна содержать прежнюю дату.

Затем сохраните результат `originalDate.plusDays(5)`
в «обновлённую дату» (`updatedDate`) типа `LocalDate` и выведите её.

Вывод:

```text
Original: 2026-06-15
Updated:  2026-06-20
```

### Диагностический эксперимент 2. Один момент в разных часовых поясах

Создайте «лондонское время для сравнения» (`diagnosticLondonTime`) типа `ZonedDateTime`
для следующих даты, времени и зоны:

```text
2026-06-15 16:00 Europe/London
```

Через `withZoneSameInstant()` преобразуйте его в `Asia/Tokyo`
и сохраните как
«токийское время для сравнения» (`diagnosticTokyoTime`) типа `ZonedDateTime`.
Сравните оба значения сначала через `isEqual()`, затем через `equals()`.

Контрольные значения:

```text
isEqual → true
equals  → false
```

`isEqual()` сравнивает момент на временной шкале.
`equals()` учитывает также остальные составляющие представления `ZonedDateTime`, включая зону.

### Диагностический эксперимент 3. Разница между `LocalDateTime` и `Instant`

Создайте «местные дата и время» (`diagnosticLocalDateTime`) типа `LocalDateTime`:

```text
2026-06-15T16:00
```

Объясните, почему это значение само по себе не задаёт единственный момент времени.
Двумя отдельными вызовами `atZone()` привяжите его к Лондону и Токио.
Сохраните результаты в «лондонское время для сравнения» (`diagnosticLondonTime`)
и «токийское время для сравнения» (`diagnosticTokyoTime`) типа `ZonedDateTime`.

Через `toInstant()` получите «лондонский момент» (`diagnosticLondonInstant`)
и «токийский момент» (`diagnosticTokyoInstant`) типа `Instant`.
Сравните их через `equals()` и убедитесь, что моменты различаются.

Не используйте здесь `withZoneSameInstant()`: одинаковые местные дата и время
в Лондоне и Токио обозначают разные реальные моменты.

### Диагностический эксперимент 4. Переход на летнее время

Создайте «время в пропущенном интервале» (`gapDateTime`) типа `LocalDateTime`:

```text
2026-03-29T01:30
```

Через `atZone()` привяжите его к `Europe/London`.
Результат сохраните в
«полученное лондонское время» (`resolvedLondonDateTime`) типа `ZonedDateTime`.
В этот день местное время `01:30` пропускается при весеннем переводе часов.

Контрольное значение:

```text
2026-03-29T02:30+01:00[Europe/London]
```

Через `toLocalDateTime()` получите «местное время после привязки зоны» (`resolvedLocalDateTime`)
типа `LocalDateTime` и сравните его с `gapDateTime`: они различаются.
Строгий разбор строки проверяет календарную дату и время,
но не отменяет правила `atZone()` для пропущенного времени в конкретной зоне.

### Диагностический эксперимент 5. Ошибка разбора даты

Создайте «некорректную дату и время» (`invalidDateTimeInput`) типа `String`:

```text
32.06.2026 14:30
```

В `TimeDiagnostics` создайте «форматтер даты и времени» (`dateTimeFormatter`)
типа `DateTimeFormatter` с шаблоном `dd.MM.uuuu HH:mm` и `ResolverStyle.STRICT`, как в этапе 2.
Попробуйте преобразовать строку через `LocalDateTime.parse()`.
Перехватите `DateTimeParseException` параметром «исключение» (`exception`)
и выведите результат `getMessage()`.
Проверяйте тип ошибки и смысл сообщения, а не посимвольное совпадение текста исключения.
После опыта восстановите рабочую версию с корректными данными.

### Диагностический эксперимент 6. `Period` против `Duration`

Создайте «начальную дату периода» (`periodStartDate`) и
«конечную дату периода» (`periodEndDate`) типа `LocalDate` соответственно:

```text
2026-04-10
2026-06-15
```

Через `Period.between()` получите
«календарный период для сравнения» (`diagnosticPeriod`) типа `Period`.

Контрольное значение:

```text
P2M5D
```

Через `ChronoUnit.DAYS.between()` получите
«число дней для сравнения» (`diagnosticDays`) типа `long`.

Контрольное значение:

```text
66
```

Создайте «начало интервала» (`intervalStart`) типа `LocalDateTime` — `15.06.2026 16:00`
и «конец интервала» (`intervalEnd`) того же типа — `15.06.2026 17:15`.
Через `Duration.between()` получите
«длительность для сравнения» (`diagnosticDuration`) типа `Duration`.
Через `toMinutes()` получите
«минуты интервала» (`diagnosticMinutes`) типа `long`: ожидается `75`.

Объясните, почему `Period` удобен для календарных дат, а `Duration` — для длительности во времени.

## 30. Критерии выполнения

Задание завершено, если:

1. `Solution` и `TimeDiagnostics` запускаются независимо;
   основной отчёт и все дополнительные тесты дают описанные результаты.
2. Разбор ввода строгий; ошибки обрабатываются отдельно, без формирования отчёта.
3. Первоначальная дата и скорректированное расписание используются по правилам этапа 6,
   а сравнение моментов, длительностей и календарных периодов соответствует этапам 10–20.
4. Диагностика показывает текущее время, совместимость с `Date`,
   високосную дату и русскоязычное представление месяца.
5. Все шесть экспериментов выполнены отдельно, временные изменения убраны.
6. Вы можете объяснить различия между локальной датой, временем суток, временем с зоной
   и абсолютным моментом, а также между `Period` и `Duration`.

Сторонние библиотеки, сервер времени, база данных и
собственные классы временных интервалов для задания не требуются.
