Задание 14. Система управления виртуальными серверами (Virtual Server Manager)

Программа регистрирует виртуальные серверы компании и позволяет изменять их состояние.
У каждого сервера есть название, количество процессорных ядер, состояние включения
и счётчик успешных перезапусков. Создайте серверы разными способами,
объедините их в список и сформируйте сводку.

Диагностический класс показывает значения полей по умолчанию и
порядок выполнения нестатических блоков инициализации и тела конструктора.
Задание закрепляет классы, объекты, поля экземпляра, перегрузку конструкторов,
`this`, ссылки и отладку в IntelliJ IDEA. Используйте Java 17 или Java 21.

## 1. Структура проекта

Создайте три файла в одном пакете задания:

* `Solution.java`            — публичный класс «решение» (`Solution`);
* `ManagedServer.java`       — публичный класс «управляемый сервер» (`ManagedServer`);
* `InitializationProbe.java` — публичный класс «проверка инициализации» (`InitializationProbe`).

Объявляйте классы с помощью `class` и модификатора `public`.
В `Solution` создайте главный метод программы:

```
public static void main(String[] args)
```

Параметр «аргументы командной строки» (`args`) типа `String[]` не используется.
Подключите `java.util.Scanner` и `java.util.ArrayList`.

`Solution` отвечает за ввод, создание объектов, вызовы методов и общую статистику.
Три вспомогательных метода статистики объявляйте `public static`.
Остальные действия выполняйте в `main`; дополнительные вспомогательные методы не требуются.

`ManagedServer` хранит состояние одного сервера. Его поля и методы относятся к экземпляру:
не объявляйте их `static`. `InitializationProbe` нужен для диагностических наблюдений;
его объект создаётся из `Solution.main`, отдельный `main` ему не требуется.

Контрольные схемы со знаком `→` и промежуточные значения служат для проверки.
Дополнительно печатать их не нужно. Постоянный вывод программы состоит
из основного отчёта этапа 13 и диагностики этапа 15, в этом порядке.

В шаблонах сообщений заменяйте обозначения в квадратных скобках фактическими значениями.
Сами скобки и поясняющий текст внутри них не печатайте.
Пробелы выравнивания из образцов записывайте внутри строковых литералов.

## 2. Этап 1. Поля класса `ManagedServer`

Объявите четыре поля экземпляра с модификатором `private`:

| Поле           | Тип       | Назначение                       |
|----------------|-----------|----------------------------------|
| `serverName`   | `String`  | Название сервера                 |
| `cpuCoreCount` | `int`     | Количество процессорных ядер     |
| `online`       | `boolean` | Включён ли сервер                |
| `restartCount` | `int`     | Количество успешных перезапусков |

Контрольные значения:

```text
online       → false
restartCount → 0
```

Каждый объект хранит собственные значения всех четырёх полей.

## 3. Этап 2. Основной конструктор

Создайте публичный конструктор:

```
public ManagedServer(String serverName, int cpuCoreCount)
```

Параметры — «название сервера» (`serverName`) типа `String`
и «количество процессорных ядер» (`cpuCoreCount`) типа `int`.
Присвойте их соответствующим полям текущего объекта.
Используйте `this`, чтобы различать поле и одноимённый параметр.

Например, при передаче следующих значений объект должен сохранить именно их:

```text
serverName   → auth-service
cpuCoreCount → 8
```

Не объявляйте возвращаемый тип конструктора, включая `void`.

## 4. Этап 3. Перегрузка конструкторов

Добавьте ещё два публичных конструктора.

### Конструктор с одним параметром

Сигнатура:

```
public ManagedServer(String serverName)
```

Параметр «название сервера» (`serverName`) типа `String` задаёт название.
Количество ядер должно равняться `2`.
Вызовите основной конструктор через `this(...)`, не дублируя присваивания полям.

### Конструктор без параметров

Сигнатура:

```
public ManagedServer()
```

Этот конструктор вызывает однопараметрический через `this(...)`.
Объект должен получить следующие значения:

```text
serverName   → unassigned-server
cpuCoreCount → 2
```

Схема делегирования конструкторов одного объекта:

```text
ManagedServer()
  ↓
ManagedServer(String)
  ↓
ManagedServer(String, int)
  ↓
Присваивания serverName и cpuCoreCount в основном конструкторе
```

Для Java 17 и Java 21 вызов `this(...)` должен быть первым оператором конструктора.
Он передаёт выполнение другому конструктору того же объекта.
Не создавайте новые объекты `ManagedServer` внутри конструкторов для делегирования.

## 6. Этап 5. Методы управления состоянием

Добавьте четыре публичных метода экземпляра.

### Запуск сервера

Метод «запустить сервер» (`startServer`) не принимает параметров и возвращает `void`.
Он устанавливает `online` в `true` и не меняет остальные поля.
Обычный запуск не увеличивает `restartCount`.

### Остановка сервера

Метод «остановить сервер» (`stopServer`) не принимает параметров и возвращает `void`.
Он устанавливает `online` в `false` и не меняет остальные поля.
Остановка не сбрасывает счётчик перезапусков.

### Перезапуск сервера

Метод «перезапустить сервер» (`restartServer`)
не принимает параметров и возвращает `boolean`.

* Если `online == false`, не меняйте поля и верните `false`.
* Если `online == true`, увеличьте `restartCount` на единицу и верните `true`.

После успешного перезапуска сервер остаётся включённым.

### Переименование сервера

Метод «переименовать сервер» (`renameServer`) принимает параметр
«название сервера» (`serverName`) типа `String` и возвращает `void`.

Через `this` присвойте параметр одноимённому полю текущего объекта.
Передаваемое название считается непустым и корректным, проверять его не требуется.
Не создавайте новый `ManagedServer` при переименовании.

## 10. Этап 9. Управление серверами

Выполните операции строго в следующем порядке:

1. Запустите `primaryServer`.
2. Запустите `secondaryServer`.
3. Дважды перезапустите `primaryServer`.
4. Один раз перезапустите `secondaryServer`.
5. Попробуйте перезапустить выключенный `reserveServer`.
6. Остановите `secondaryServer`.

Каждый результат вызова `restartServer()` сохраните в соответствующей переменной типа `boolean`:

* «Первый перезапуск основного сервера успешен» (`firstPrimaryRestartSucceeded`).
* «Второй перезапуск основного сервера успешен» (`secondPrimaryRestartSucceeded`).
* «Перезапуск второго сервера успешен» (`secondaryRestartSucceeded`).
* «Перезапуск резервного сервера успешен» (`reserveRestartSucceeded`).

Контрольные значения:

```text
firstPrimaryRestartSucceeded  → true
secondPrimaryRestartSucceeded → true
secondaryRestartSucceeded     → true
reserveRestartSucceeded       → false
```

Итоговые состояния:

| Сервер    | Включён | Перезапуски |
|-----------|---------|------------:|
| Основной  | `true`  |         `2` |
| Второй    | `false` |         `1` |
| Резервный | `false` |         `0` |

## 11. Этап 10. Две ссылки на один объект

Создайте «псевдоним основного сервера» (`primaryServerAlias`) типа `ManagedServer`
и присвойте ему значение `primaryServer`. Не используйте `new`.

Через `primaryServerAlias` вызовите `renameServer()` с названием `"auth-service-v2"`.
Затем создайте две переменные типа `boolean`:

* «Ссылки указывают на один объект» (`isSameServerReference`)     —
  результат `primaryServer == primaryServerAlias`;
* «Основной и второй серверы различаются» (`areServersDifferent`) —
  результат `primaryServer != secondaryServer`.

Обе проверки должны дать `true`.
Здесь `==` и `!=` сравнивают ссылки, а не текстовое содержимое полей.

Переименование должно быть видно через обе ссылки: объект один.
В этапе 13 выведите названия, полученные через `getServerName()`
у `primaryServer` и `primaryServerAlias`:

```text
Primary server name: auth-service-v2
Alias server name:   auth-service-v2
```

Сейчас только подготовьте данные; этот фрагмент входит в итоговый отчёт.

## 13. Этап 12. Сводная статистика

В `Solution` создайте три публичных статических метода.
Их параметр «зарегистрированные серверы» (`registeredServers`)
типа `ArrayList<ManagedServer>` — список для подсчёта.

В каждом методе используйте `for-each` и переменную
«текущий сервер» (`server`) типа `ManagedServer`.
Методы возвращают результат через `return` и ничего не печатают.
Обрабатывайте каждый элемент списка, не ограничиваясь тремя серверами основного теста.
Для пустого списка каждый метод возвращает `0`.

### Общее количество процессорных ядер

Сигнатура:

```
public static int calculateTotalCpuCores(
        ArrayList<ManagedServer> registeredServers)
```

Создайте «общее количество ядер» (`totalCpuCores`) типа `int` со значением `0`.
При обходе добавляйте значения `server.getCpuCoreCount()`.
Верните накопленную сумму; для основного теста она равна `12`.

### Количество включённых серверов

Сигнатура:

```
public static int countOnlineServers(
        ArrayList<ManagedServer> registeredServers)
```

Создайте «количество включённых серверов» (`onlineServerCount`)
типа `int` со значением `0`.
Увеличивайте счётчик только для элементов, у которых `server.isOnline()` возвращает `true`.
Верните результат; для основного теста он равен `1`.

### Общее количество перезапусков

Сигнатура:

```
public static int calculateTotalRestarts(
        ArrayList<ManagedServer> registeredServers)
```

Создайте «общее количество перезапусков» (`totalRestartCount`)
типа `int` со значением `0`.
При обходе складывайте значения `server.getRestartCount()`.
Верните сумму; для основного теста она равна `3`.

В `main` вызовите все три метода с `registeredServers`.
Результаты сохраните в переменных типа `int`:
`totalCpuCores`, `onlineServerCount` и `totalRestartCount` соответственно.
Эти переменные находятся в `main`, отдельно от одноимённых накопителей внутри методов.

## 15. Этап 14. Диагностический класс `InitializationProbe`

Объявите три поля экземпляра с модификатором `private`:

| Поле                  | Тип      | Начальное значение |
|-----------------------|----------|--------------------|
| `defaultCounter`      | `int`    | Не задавать явно   |
| `defaultLabel`        | `String` | Не задавать явно   |
| `initializationStage` | `int`    | `1`                |

«Счётчик по умолчанию» (`defaultCounter`) и «метка по умолчанию» (`defaultLabel`)
должны получить стандартные значения Java автоматически.
«Этап инициализации» (`initializationStage`) инициализируйте при объявлении поля.

### Первый нестатический блок инициализации

После объявления полей создайте нестатический блок.
При создании каждого объекта он должен:

1. Вывести текущее значение `initializationStage`.
2. Изменить его на `5`.

Вывод для исходного кода:

```text
INIT BLOCK 1: stage = 1
```

### Второй нестатический блок инициализации

Ниже первого блока создайте второй.
Он выводит текущее значение `initializationStage`, но не изменяет поле.

Вывод для исходного кода:

```text
INIT BLOCK 2: stage = 5
```

### Конструктор

Создайте публичный конструктор `InitializationProbe()` без параметров.
В его теле выведите текущее значение `initializationStage`:

```text
CONSTRUCTOR:  stage = 5
```

Во всех трёх сообщениях подставляйте значение поля.
Не записывайте `1` или `5` в команды вывода как готовый результат:
диагностика должна отражать изменения кода во временных экспериментах.

### Методы доступа

Создайте три публичных метода экземпляра без параметров:

| Метод                      | Тип результата | Возвращаемое поле     |
|----------------------------|----------------|-----------------------|
| `getDefaultCounter()`      | `int`          | `defaultCounter`      |

| `getInitializationStage()` | `int`          | `initializationStage` |

Каждый метод возвращает соответствующее поле через `return`,
не изменяет его и ничего не печатает.

## 16. Этап 15. Проверка порядка инициализации

В конце `Solution.main`, после основного отчёта, создайте
«диагностический экземпляр» (`initializationProbe`) типа `InitializationProbe`
через `new InitializationProbe()`.

При создании этого объекта:

1. Поля получают значения по умолчанию:
   `defaultCounter` — `0`, `defaultLabel` — `null`, `initializationStage` — `0`.
2. Выполняется присваивание `initializationStage = 1` при объявлении поля.
3. Первый нестатический блок печатает `1` и меняет поле на `5`.
4. Второй нестатический блок печатает `5`.
5. Тело конструктора печатает `5`.

Затем через методы доступа выведите итоговые значения трёх полей.

Вывод:

```text
INIT BLOCK 1: stage = 1
INIT BLOCK 2: stage = 5
CONSTRUCTOR:  stage = 5
Default counter: 0
Default label:   null
Final stage:     5
```

Первые три строки появляются автоматически при создании объекта.
Последние три строки, начиная с `Default counter`, выведите из `Solution.main`.
Выравнивание сообщений о порядке инициализации и итоговых полей задаётся отдельно.

Не создавайте метод для запуска блоков инициализации:
они выполняются автоматически для каждого нового объекта.

## 17. Этап 16. Отладка в IntelliJ IDEA

## 19. Диагностические эксперименты

Выполняйте эксперименты по одному после успешного основного теста.
Временные объекты не добавляйте в `registeredServers`.
После каждого опыта удаляйте временный код, восстанавливайте изменённые части программы
и повторяйте основной тест. Намеренные ошибки компиляции не должны оставаться активными.

### Диагностический эксперимент 1. Отсутствие конструктора без параметров

Временно удалите конструктор `public ManagedServer()`.
Попытка создания объекта через `new ManagedServer()` должна вызвать ошибку компиляции:
в классе останутся только конструкторы с параметрами.

Верните конструктор без параметров.
Объясните, почему Java не добавляет его автоматически,
когда в классе уже объявлены собственные конструкторы.

### Диагностический эксперимент 2. Неправильное расположение `this(...)`

Временно вставьте команду вывода перед `this(...)` в конструкторе с одним параметром.
Для Java 17 и Java 21 это должно вызвать ошибку компиляции.
Восстановите правильный порядок.

### Диагностический эксперимент 3. Приватное поле

В `Solution.main` временно попробуйте вывести `primaryServer.restartCount`
через `System.out.println()`.

Ошибка компиляции должна быть связана с недоступностью приватного поля из другого класса.
Не записывайте обращение к полю отдельной командой без вывода:
это добавило бы другую синтаксическую ошибку.
После наблюдения удалите временную команду.
Для обычного чтения поля используйте `getRestartCount()`.

### Диагностический эксперимент 4. Ссылка на тот же объект

Создайте «псевдоним второго сервера» (`secondaryServerAlias`) типа `ManagedServer`.
Присвойте ему `secondaryServer` без вызова `new`.
Через новую ссылку вызовите `startServer()`.

Проверьте через `secondaryServer.isOnline()`, что изменение видно по исходной ссылке.
Затем остановите сервер и восстановите состояние основного теста.

### Диагностический эксперимент 5. Независимые экземпляры

Создайте два новых объекта типа `ManagedServer` через конструктор с двумя параметрами:

* «Первый тестовый сервер» (`firstTestServer`)  — название `"test-a"`, число ядер `2`;
* «Второй тестовый сервер» (`secondTestServer`) — название `"test-b"`, число ядер `2`.

Запустите только первый.
Через методы доступа убедитесь, что второй остался выключенным:
это разные объекты с независимыми полями `online`.

### Диагностический эксперимент 6. Значения полей по умолчанию

В `InitializationProbe` временно уберите присваивание `1`
при объявлении поля `initializationStage`.
Не меняя остальную логику, запустите программу.

Первый блок должен увидеть значение по умолчанию `0`, а не `1`.
После его выполнения поле станет равным `5`, как в исходном сценарии.
Верните инициализацию поля при объявлении значением `1`.

### Диагностический эксперимент 7. Порядок блоков инициализации

Временно поменяйте местами два нестатических блока `InitializationProbe`,
сохранив их команды и подписи.

Порядок диагностических сообщений:

```text
INIT BLOCK 2: stage = 1
INIT BLOCK 1: stage = 1
CONSTRUCTOR:  stage = 5
```

Блок с подписью `INIT BLOCK 2` теперь выполняется первым и видит `1`.
Следующий блок тоже печатает `1`, затем устанавливает `5`.
Тело конструктора видит уже изменённое значение.

Восстановите исходный порядок.
Блоки выполняются сверху вниз по расположению в классе, а не по числам в подписях.

### Диагностический эксперимент 8. Инициализация каждого нового объекта

В `Solution.main` сразу после создания `initializationProbe` создайте второй объект
«второй диагностический экземпляр» (`secondInitializationProbe`)
типа `InitializationProbe` через конструктор без параметров.

Последовательность:

```text
INIT BLOCK 1: stage = 1
INIT BLOCK 2: stage = 5
CONSTRUCTOR:  stage = 5
```

должна появиться два раза — отдельно для каждого объекта.
Чтение итоговых полей первого объекта оставьте после создания обоих.
После опыта верните один диагностический экземпляр.

### Диагностический эксперимент 9. `null` вместо объекта

Создайте отдельную временную переменную «отсутствующий сервер» (`nullServer`)
типа `ManagedServer` со значением `null`.
Попробуйте вызвать через неё `startServer()`.

Поместите вызов в отдельный `try/catch`.
Перехватите `NullPointerException` параметром «исключение» (`exception`)
и убедитесь, что выполнение перешло в обработчик.
После опыта удалите демонстрационный код.

Объясните различие между ссылкой, равной `null`,
и ссылкой на существующий объект.

### Диагностический эксперимент 10. Инструменты IntelliJ IDEA

Создайте «временный сервер» (`temporaryServer`) типа `ManagedServer`
через конструктор без параметров, отдельно от основного списка.
Примените инструменты редактора к собственному коду:

* `Shift+F6`                     — безопасно переименуйте
  `temporaryServer` в `renamedTemporaryServer`;
* `Ctrl+Alt+L`                   — отформатируйте код;
* дважды `Shift`                 — найдите класс через Search Everywhere;
* `Ctrl+Alt+T`                   — ознакомьтесь с Surround With на временно выделенном фрагменте;
* `psvm`, `sout`, `fori`, `iter` — попробуйте шаблоны редактора там, где они применимы.

Сочетания клавиш зависят от раскладки, как указано в этапе 16.
Сохраните содержательные имена переменных и методов основного задания.
Удалите временный объект и случайно добавленные конструкции после эксперимента.

## 21. Критерии выполнения

Задание завершено, если:

1. Три публичных класса находятся в отдельных Java-файлах одного пакета
   и программа компилируется на Java 17 или Java 21.
2. Поля серверов принадлежат экземплярам; конструкторы, методы доступа
   и изменения состояния работают по этапам 1–6.
3. Основной сценарий сохраняет независимость серверов и общность объекта у двух ссылок;
   отчёт и все шесть дополнительных тестов дают описанные результаты.
4. Диагностика показывает значения по умолчанию и порядок выполнения присваивания при объявлении,
   нестатических блоков и тела конструктора.
5. Отладка этапа 16 и все десять экспериментов выполнены; временные изменения убраны.
6. Вы можете объяснить различия между классом, объектом, полем, методом и конструктором,
   между полем экземпляра и локальной переменной, а также перегрузку конструкторов,
   делегирование через `this(...)` и две ссылки на один объект.

Наследование, интерфейсы, абстрактные классы, переопределение `equals()` и `hashCode()`,
база данных и реальный сервер в этом задании не требуются.
