Отличия record и class, ограничения record

## 1. Сравнение `record` и `class`: в чём главные отличия?

В Java для описания моделей данных часто используют обычные классы (`class`)
и record-классы (`record`). На первый взгляд, оба варианта позволяют
хранить и обрабатывать данные. Но если копнуть чуть глубже,
различий больше, чем может показаться!

### Таблица отличий: `class` vs `record`

| Характеристика     | Обычный класс (`class`)              | Record-класс (`record`)             |
|--------------------|--------------------------------------|-------------------------------------|
| **Изменяемость**   | Поля могут быть `final` или нет      | Компоненты — `final`                |
| **Наследование**   | `extends`, если не `final`           | Всегда `final`                      |
| **Поля**           | Любых типов, с `static` или без него | Компоненты и статические поля       |
| **Методы доступа** | Вручную или с помощью Lombok         | `name()` и др. автоматически        |
| **Сеттеры**        | Можно объявить                       | Не генерируются; поля менять нельзя |

| Характеристика     | Обычный класс (`class`)              | Record-класс (`record`)       |
|--------------------|--------------------------------------|-------------------------------|
| **`equals` и др.** | Переопределяются вручную или IDE     | Автогенерация по компонентам  |
| **Конструкторы**   | Любые, сколько угодно                | Канонический и дополнительные |
| **Интерфейсы**     | Может реализовывать                  | Может реализовывать           |
| **Доп. методы**    | Любые                                | Можно добавлять свои методы   |
| **Коллекции**      | Нужны корректные `equals`/`hashCode` | Сгенерированы по компонентам  |

Все поля компонентов `record` имеют модификаторы `private final`, однако
сами объекты, на которые ссылаются компоненты, могут быть изменяемыми.
Дополнительные нестатические поля в `record` запрещены, а статические поля
разрешены. Канонический конструктор можно записать в компактной форме. Дополнительный
конструктор с другой сигнатурой делегирует через `this(...)`.

В `record` автоматически создаются методы доступа с именами компонентов
(например, `name()`), но не обычные геттеры вида `getName()`.
`equals()`, `hashCode()` и `toString()` генерируются автоматически,
если не переопределены явно. При использовании `record` в качестве ключа
коллекции компоненты должны иметь стабильные значения для сравнения и хэширования.

### Пример для наглядности

Обычный класс:

```
// Person.java — схематический пример: тела трёх методов сокращены
public class Person {
    private final String name;
    private final int age;

    public Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    public String getName() { return name; }
    public int getAge() { return age; }

    @Override
    public boolean equals(Object o) { /* ... */ }
    @Override
    public int hashCode() { /* ... */ }
    @Override
    public String toString() { /* ... */ }
}
```

Здесь методы `equals()`, `hashCode()` и `toString()` показаны схематически:
без их тел этот фрагмент не компилируется.

Record-класс:

```
// Person.java — альтернативный вариант
public record Person(String name, int age) { }
```

Всё! Одна строчка кода — и мы получаем готовый тип с конструктором,
методами доступа и реализациями `equals()`, `hashCode()` и `toString()`.
В отличие от обычного класса, его компоненты нельзя переназначить после создания.
И никаких рисков забыть реализовать что-то важное.

## 2. Ограничения record-классов

Record-классы — это не просто «короткий синтаксис», а отдельная концепция,
у которой есть свои строгие правила. Давайте рассмотрим их подробнее.

### `record` всегда `final`

Record-класс по определению всегда `final`. Это значит, вы не можете создать
подкласс от `record`:

```
// Point.java
public record Point(int x, int y) { }

// public class ColoredPoint extends Point { } // Ошибка компиляции!
```

Если вам нужно расширять поведение, используйте обычные классы или композицию
(вложите `record` в класс).

### `record` не может быть суперклассом

Record-класс не может быть родителем для других классов, поскольку он всегда `final`.
Его назначение — явно представлять фиксированный набор компонентов, а не служить
основой изменяемой иерархии объектов.

### Только `final`-поля (компоненты)

Все компоненты `record` объявляются в заголовке и становятся `private final`.
Вы не можете добавить нестатические поля в тело `record`:

```
// User.java
public record User(String login, String email) {
    // int counter;             // Ошибка! Нельзя добавлять нестатические поля
    static int totalUsers = 0;  // Можно, это статическое поле
}
```

### Нет сеттеров, изменяющих компоненты

Record-класс не может иметь сеттеров, которые меняют значения компонентов.
Метод с названием `setX(int x)` объявить можно, но присвоить в нём
новое значение полю после создания объекта нельзя.

```
// Point.java — альтернативный вариант
public record Point(int x, int y) {
    // public void setX(int x) { this.x = x; } // Ошибка: нельзя изменить final-поле
}
```

### Конструктор без параметров не создаётся автоматически при наличии компонентов

У `record` есть канонический конструктор со всеми компонентами.
Если в заголовке указаны `x` и `y`, автоматически доступен `Point(int x, int y)`,
но не `Point()`:

```
Point p = new Point(1, 2);  // ОК
// Point p = new Point();   // Ошибка: нет конструктора без параметров
```

Однако можно явно добавить конструктор без параметров, который вызывает
канонический через `this(...)`:

```
// Point.java — ещё один вариант
public record Point(int x, int y) {
    public Point() {
        this(0, 0);
    }
}
```

Если компонентов нет (`record Empty() {}`), канонический конструктор
сам будет без параметров.

### Нет нестатических инициализаторов

Record-класс не может содержать нестатические блоки инициализации
(те, что пишутся в фигурных скобках вне методов):

```
// User.java — альтернативный вариант
public record User(String login) {
    // { /* ... */ } // Ошибка: нестатические инициализаторы запрещены
}
```

Статические блоки инициализации разрешены.

### Ограничения по наследованию

Record-класс не может явно наследовать другой класс. Все `record` неявно наследуют
`java.lang.Record`. Но реализовывать интерфейсы — пожалуйста!

```
// Printable.java
public interface Printable {
    void print();
}
```

```
// Book.java
public record Book(String title) implements Printable {
    @Override
    public void print() {
        System.out.println("Печатаем книгу: " + title);
    }
}
```

### Не подходит для сложной бизнес-логики

`record` — это прежде всего про данные, а не про сложное поведение.
Если у вашего объекта изменяемое состояние, «жизненный цикл» или куча зависимостей,
лучше использовать обычный класс. При этом Java не запрещает объявлять
в `record` дополнительные методы, даже с нетривиальной логикой.

## 3. Когда стоит использовать record-классы?

* **DTO (Data Transfer Object)**: для передачи данных между слоями приложения,
  сервисами, микросервисами или REST-контроллерами (например, в JSON-ответах).
* **Value Object**: объекты, которые определяются только своими значениями.
* **Ключи и значения в коллекциях**: когда важна корректная реализация
  `equals()` и `hashCode()` (например, для `HashMap` или `Set`).
* **Результаты вычислений**: когда нужно вернуть из метода сразу несколько
  значений (например, `record Pair<T, U>(T first, U second) {}`).

### Пример: DTO для REST-контроллера

```
// UserDto.java
public record UserDto(String login, String email) { }
```

Такой объект удобно возвращать из контроллера: после создания нельзя переназначить
его компоненты. Для передачи в JSON потребуется поддержка `record` используемой
библиотекой сериализации.

### Пример: ключ для `HashMap`

```
// Point.java
public record Point(int x, int y) { }
```

```
// Main.java
import java.util.HashMap;
import java.util.Map;

public class Main {
    public static void main(String[] args) {
        Map<Point, String> pointNames = new HashMap<>();
        pointNames.put(new Point(1, 2), "A");
        pointNames.put(new Point(3, 4), "B");

        // Всё работает: equals() и hashCode() уже реализованы!
        System.out.println(pointNames.get(new Point(1, 2))); // A
    }
}
```

## 4. Когда record-классы использовать НЕ стоит

* **Изменяемое состояние**: если поле объекта должно меняться после создания.
* **Сложная логика**: если у объекта сложное поведение, много методов,
  вложенные объекты с изменяемым состоянием.
* **Наследование**: если требуется иерархия классов, абстрактные базовые
  классы, переопределение методов в подклассах.
* **Сущности бизнес-логики**: например, объекты, которые живут в базе данных
  и имеют уникальный идентификатор.

### Пример: когда нужен обычный класс

```
// Account.java
public class Account {
    private String id;
    private int balance;

    public Account(String id, int balance) {
        this.id = id;
        this.balance = balance;
    }

    public void deposit(int amount) { balance += amount; }
    public void withdraw(int amount) { balance -= amount; }
    // getters, setters, equals, hashCode, toString...
}
```

Здесь явно видно, что состояние объекта меняется — `record` не подходит.
Методы приведены для иллюстрации изменяемости; в настоящем банковском приложении
понадобятся проверка сумм и более подходящий тип для денежных расчётов.

## 5. Практические примеры: выбираем между `record` и `class`

### Пример: `record` — идеальный выбор

```
// Rectangle.java
public record Rectangle(int width, int height) {
    public int area() {
        return width * height;
    }
}
```

* Прямоугольник определяется только шириной и высотой.
* Нет необходимости менять эти значения после создания.
* Можно добавить полезный метод `area()`.
* Всё остальное Java сделает за вас.

### Пример: `class` — лучший вариант

```
// MutableRectangle.java
public class MutableRectangle {
    private int width;
    private int height;

    public MutableRectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }

    public void setWidth(int width) { this.width = width; }
    public void setHeight(int height) { this.height = height; }

    public int area() { return width * height; }
}
```

Нужно изменять размеры прямоугольника после создания? Используйте обычный класс.

## 6. Типичные ошибки при работе с record-классами

### Ошибка № 1. Попытка добавить нестатическое поле

Record-класс не позволяет объявлять нестатические поля вне списка компонентов.
Если попытаться — компилятор выдаст ошибку. Например:

```
// City.java
public record City(String name) {
    // int population; // Ошибка!
}
```

### Ошибка № 2. Желание добавить сеттер

`record` не поддерживает изменение компонентов через сеттеры. Любая попытка
присвоить полю новое значение после создания объекта — ошибка компиляции.
Само имя метода `setX()` не запрещено.

### Ошибка № 3. Попытка наследовать `record` или от `record`

`record` всегда `final`. Нельзя наследовать от `record`, и `record` не может явно
наследовать другой класс (кроме неявного `java.lang.Record`).

### Ошибка № 4. Использование `record` для изменяемых объектов

Если вы планируете менять состояние самого объекта после создания — `record`
не для вас! Используйте обычный класс. Если же компонент ссылается на изменяемый
объект, его содержимое может изменяться, несмотря на `final` у поля `record`.

### Ошибка № 5. Забыли про ограничения конструктора

У `record` есть канонический конструктор со всеми компонентами. Конструктор
без параметров автоматически появится только у `record` без компонентов.
Для `record` с компонентами его можно объявить отдельно, вызвав `this(...)`.
