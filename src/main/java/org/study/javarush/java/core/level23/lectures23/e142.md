Проблемы полиморфизма и абстракций

## 1. Полиморфизм: что это и зачем нужен

Если вы думаете, что полиморфизм — это что-то из мира мутантов Marvel, спешу разочаровать:
в программировании всё куда спокойнее, но не менее волшебно. Полиморфизм — это способность
объектов с разной реализацией реагировать на одни и те же вызовы методов по-разному.

Пример из жизни:

У вас есть класс `Book` и класс `Magazine`, оба наследуются от абстрактного класса
`LibraryItem`. Вы хотите, чтобы для любого элемента библиотеки можно было вызвать метод
`printInfo()`, и он выведет нужную информацию: для книги — автора и название, для журнала —
номер выпуска.

Пример кода:

```
abstract class LibraryItem {
    String title;

    LibraryItem(String title) {
        this.title = title;
    }

    abstract void printInfo();
}

class Book extends LibraryItem {
    String author;

    Book(String title, String author) {
        super(title);
        this.author = author;
    }

    String getAuthor() {
        return author;
    }

    @Override
    void printInfo() {
        System.out.println("Книга: " + title + ", автор: " + author);
    }
}

class Magazine extends LibraryItem {
    int issueNumber;

    Magazine(String title, int issueNumber) {
        super(title);
        this.issueNumber = issueNumber;
    }

    @Override
    void printInfo() {
        System.out.println("Журнал: " + title + ", выпуск: " + issueNumber);
    }
}
```

Теперь можно создать массив из разных элементов и вызвать `printInfo()` для каждого:

```
LibraryItem[] items = {
    new Book("Повелитель мух", "Вильям Голдинг"),
    new Magazine("Наука и жизнь", 5)
};

for (LibraryItem item : items) {
    item.printInfo();
}
```

Вывод:

```text
Книга: Повелитель мух, автор: Вильям Голдинг
Журнал: Наука и жизнь, выпуск: 5
```

**Вот так работает полиморфизм!**

## 2. Типичные ошибки с полиморфизмом

### Попытка вызвать методы, которых нет в базовом типе

Одна из самых частых ошибок — попытка обратиться к методу, который объявлен только в дочернем
классе, через ссылку на базовый тип.

```
LibraryItem item = new Book("Гарри Поттер", "Дж. Роулинг");
// item.getAuthor(); // Ошибка компиляции! В LibraryItem нет метода getAuthor().
```

Java проверяет доступность методов по типу переменной (`LibraryItem`), а не по фактическому
классу объекта (`Book`). Поэтому если вам нужно вызвать специфичный для книги метод,
можно проверить тип и выполнить приведение:

```
if (item instanceof Book) {
    Book book = (Book) item;
    System.out.println(book.getAuthor());
}
```

Здесь метод `getAuthor()` существует в классе `Book` из первого примера. Если такого метода
нет даже в `Book`, само приведение типа проблему не решит.

### Приведение типов без проверки

Если вы уверены, что объект — это `Book`, но на самом деле это не так, получите
`ClassCastException` во время выполнения. Например:

```
LibraryItem item = new Magazine("Forbes", 12);
Book book = (Book) item; // БУМ! ClassCastException.
```

Правильный способ при неизвестном фактическом типе — проверить его:

```
if (item instanceof Book) {
    Book book = (Book) item;
    System.out.println(book.getAuthor());
} else {
    System.out.println("Это не книга!");
}
```

Если тип уже гарантирован логикой программы, отдельная проверка не всегда необходима.
Но по возможности лучше работать через общие методы абстракции без приведения типов.

### Неиспользование преимуществ полиморфизма

Иногда разработчики пишут код так, что он жёстко привязан к конкретным типам, хотя можно
было бы использовать абстракции. Например:

```
Book[] books = ...;
for (Book book : books) {
    book.printInfo();
}
```

Это работает только для книг. А если завтра появятся журналы, газеты, комиксы?
Лучше использовать массив `LibraryItem[]` и работать с методами базового класса или интерфейса.

## 3. Абстракции: зачем они нужны и как их не испортить

### Абстрактные классы и интерфейсы

Абстракция — это искусство выделять главное и скрывать детали. В Java для этого есть
абстрактные классы и интерфейсы.

**Абстрактный класс** — это класс, экземпляр которого нельзя создать напрямую.
Он может содержать общее состояние и поведение для наследников.

**Интерфейс** — это контракт: что должен уметь класс. При этом интерфейс может содержать
и методы с реализацией, например `default`-методы.

### Ошибка № 1. Выбор абстрактного класса без ясной цели

Если в вашем абстрактном классе нет ни одного абстрактного метода, задумайтесь —
а точно ли он должен быть абстрактным? Может, проще сделать обычный класс?

```
abstract class UselessAbstract {
    void sayHello() {
        System.out.println("Hello!");
    }
}
```

Такой класс корректен в Java. Абстрактность может быть полезна, например, чтобы
запретить создание экземпляров базового класса, даже когда все его методы реализованы.

### Ошибка № 2. Отсутствие реализации обязательных методов в наследниках

Если конкретный класс наследует абстрактный класс или реализует интерфейс, он обязан
обеспечить реализации всех обязательных абстрактных методов. Если забыть — компилятор
напомнит. Но бывает, что методы реализованы «для галочки» и ничего не делают.
Это плохо для поддержки кода.

```
class Magazine extends LibraryItem {
    Magazine(String title, int issueNumber) {
        super(title);
        // ...
    }

    @Override
    void printInfo() {
        // Пусто! Плохо!
    }
}
```

В этом фрагменте метод реализован формально, поэтому ошибка компиляции из-за
`printInfo()` не возникнет. Но ожидаемого поведения не будет.

### Ошибка № 3. Слишком глубокая или запутанная иерархия абстракций

Когда классы наследуются друг от друга в пять–десять уровней, разобраться в них
становится очень сложно. Лучше делать «плоские» иерархии, где всё понятно.

Плохой пример:

```text
LibraryItem
    |
BookItem
    |
PrintedBook
    |
IllustratedBook
    |
ChildrenIllustratedBook
```

Сложно, не правда ли? Часто достаточно двух-трёх уровней, но это рекомендация,
а не ограничение языка Java. Глубина иерархии должна соответствовать задаче.

## 4. Практика: применение полиморфизма и абстракций в учебном приложении

Давайте доработаем ваше учебное приложение для библиотеки. Ранее у вас были только книги.
Теперь добавим журналы и реализуем общий тип для печатных изданий.

Объявим абстрактный класс:

```
// LibraryItem.java
abstract class LibraryItem {
    protected String title;

    public LibraryItem(String title) {
        this.title = title;
    }

    public abstract void printInfo();
}
```

Добавим дочерние классы:

```
// Book.java
class Book extends LibraryItem {
    private String author;

    public Book(String title, String author) {
        super(title);
        this.author = author;
    }

    @Override
    public void printInfo() {
        System.out.println("Книга: " + title + ", автор: " + author);
    }
}
```

```
// Magazine.java
class Magazine extends LibraryItem {
    private int issueNumber;

    public Magazine(String title, int issueNumber) {
        super(title);
        this.issueNumber = issueNumber;
    }

    @Override
    public void printInfo() {
        System.out.println("Журнал: " + title + ", выпуск: " + issueNumber);
    }
}
```

Используем полиморфизм:

```
LibraryItem[] items = {
    new Book("Чистый код", "Роберт Мартин"),
    new Magazine("Java World", 3)
};

for (LibraryItem item : items) {
    item.printInfo();
}
```

### Добавим интерфейс для электронных изданий

Допустим, некоторые издания можно читать онлайн. Введём интерфейс:

```
// ReadableOnline.java
interface ReadableOnline {
    void openOnline();
}
```

```
// EBook.java
class EBook extends Book implements ReadableOnline {
    private String url;

    public EBook(String title, String author, String url) {
        super(title, author);
        this.url = url;
    }

    @Override
    public void openOnline() {
        System.out.println("Открываем электронную книгу по адресу: " + url);
    }
}
```

Теперь можно работать с электронными книгами через интерфейс:

```
ReadableOnline ebook = new EBook("Java для чайников", "Барри Берд", "https://example.com/java");
ebook.openOnline();
```

## 5. Как избежать проблем с полиморфизмом и абстракциями: best practices

* **Используйте интерфейсы для описания возможностей, а абстрактные классы — для общего
  поведения и, при необходимости, состояния.** Например, интерфейс `Printable` хорошо
  описывает возможность «печати», а хранить в интерфейсе обычное поле `String title`
  нельзя: поля интерфейса не являются полями экземпляра.
* **Проверяйте тип объекта с помощью `instanceof` перед небезопасным приведением.**
  Особенно если фактический тип может различаться. Это убережёт от `ClassCastException`.
  По возможности избегайте приведения типов, пользуясь общими методами.
* **Стремитесь к «плоским» и понятным иерархиям.** Чем проще дерево наследования —
  тем легче поддерживать и расширять код.
* **Старайтесь не делать «бессмысленных» абстракций.** Если класс не содержит
  абстрактных методов и не предназначен для наследования — не делайте его абстрактным.
* **Используйте аннотацию `@Override` при переопределении метода.**
  Это помогает компилятору ловить ошибки в сигнатуре.

## 6. Типичные ошибки при работе с полиморфизмом и абстракциями

### Ошибка № 1. Приведение типа без проверки

Иногда хочется «срезать угол» и привести тип без проверки. Это может сработать,
а может привести к внезапному падению программы. Если тип заранее не гарантирован,
используйте `instanceof`:

```
if (item instanceof Book) {
    Book book = (Book) item;
    // ...
}
```

### Ошибка № 2. Попытка вызвать метод дочернего класса через ссылку на базовый тип

```
LibraryItem item = new Book("Java", "Автор");
item.getAuthor(); // Ошибка компиляции: в LibraryItem нет такого метода!
```

Решение — либо привести тип (если у `Book` есть такой метод), либо добавить нужный метод
в базовый класс, если это логично.

### Ошибка № 3. Неполная реализация интерфейса или абстрактного класса

Если конкретный класс не реализовал все обязательные абстрактные методы — компилятор
не даст собрать проект. Но если реализовать «заглушки», которые ничего не делают,
это приведёт к неожиданному поведению.

### Ошибка № 4. Слишком глубокая иерархия наследования

Если у вас больше трёх уровней наследования — задумайтесь, нельзя ли упростить архитектуру.
Это не жёсткое ограничение: иногда более глубокая иерархия оправданна.

### Ошибка № 5. Нарушение принципа единой ответственности

Если абстракция описывает слишком много обязанностей, она становится
трудноподдерживаемой. Лучше разбивать на несколько интерфейсов или классов.
